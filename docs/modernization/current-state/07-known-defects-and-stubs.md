# LIFE400 Known Defects, Stubs and Inert Features

This document is the disposition register for the LIFE400 estate. It collects every defect, stub, inert feature and internal contradiction that the current-state layer established with evidence, and it assigns each one exactly one decision: **migrate**, **implement** or **drop**. Seventeen entries are recorded, identified `DEF-01` through `DEF-17`, and each carries the source line that establishes it. This is the last document in the layer and the only one that decides anything: documents one through six state what is true, and this one states what is to become of it.

**Scope.** This register decides dispositions and stops there. It assigns no severity and designs no control — anything security-relevant below is registered for severity in [the security risk register](../risk/01-security-risk-register.md) and closed by a control in [the security control design](../target-state/04-security-control-design.md). It performs no continuity analysis: atomicity, recovery objectives and reconciliation belong to [the continuity and recovery risk document](../risk/03-continuity-and-recovery-risk.md). It publishes no target column, type or constraint — that is [the target data model and schema mapping](../target-state/03-target-data-model-and-schema-mapping.md) — and no target screen or route, which is [the UI modernization document](../target-state/05-ui-modernization.md). It restates no schema, no [paragraph](../reference/glossary-ibm-i.md#paragraph) inventory and no rule census; each of those has one owning document, cited where it is used. A disposition here is a decision about a known fact, not a design.

**Reading the citations.** Every claim carries an inline citation of the form `[<path>:<locator>]` immediately after the claim. Citations are plain text and deliberately not hyperlinks: a plain-text citation stays meaningful in a diff and does not depend on a hosting provider's line-anchor syntax. Open the member to read the statement in place. Platform terms link to [the IBM i glossary](../reference/glossary-ibm-i.md) on first use in this document.

**Nothing here was fixed.** This is a register of observations and recommendations, and every one of the 24 members is left exactly as it stands. No source member is annotated, corrected, reformatted or commented by this documentation set, and the machine-generated corpus under `.swm/` is neither edited nor reproduced. Three entries below are especially easy to misread as invitations to edit — a superseded company name on a live screen, a stale filename in a source comment, and a spurious file [override](../reference/glossary-ibm-i.md#override) — and none of them is touched. The correction each row proposes is a target-side action, recorded so that it happens deliberately and once, in the target, rather than opportunistically in an estate that has no test suite to catch a mistake.

**How this register was assembled.** Each entry began as an observation published by one of the six preceding documents, which state facts and explicitly defer disposition here. Every anchor was then re-verified by opening the member and confirming that the cited line holds the construct claimed, because a citation that resolves to a real line but points at the wrong statement is worse than no citation: it survives every automated check and misleads every reader. Absence claims — that no program names a [printer file](../reference/glossary-ibm-i.md#printer-file), that no statement assigns a status, that no handler exists for a command key — were established by searching all 24 members rather than by inspecting the places the behaviour was expected. Where two parts of the system disagree, both positions are recorded and the disagreement itself is the entry; this register does not silently pick a winner and then document the winner as fact.

## Why a register, and why every row forces a decision

A defect carried forward silently becomes a defect in the target. A stub carried forward silently becomes a missing feature discovered after cutover, when the system that used to be a reference is gone. Both failures share one cause: an observation that stayed an observation. This system offers unusually many opportunities for that. A nightly job whose sweep is a placeholder still completes successfully every run. A menu option that reports its own absence still appears to every user. Two report layouts that no program produces still exist as compiled objects. A status value that nothing can assign is still guarded against in two programs. Each of those reads, at a glance, like working software.

The estate also offers no safety net that would catch the omission later. There is no test member and no test-runner configuration anywhere in the repository, so nothing fails when a behaviour quietly disappears, and no build step compares the estate against a description of itself. That absence is why conversion is gated on a behavioural baseline in [MOD-ADR-008 on characterization tests first](../decisions/MOD-ADR-008-characterization-tests-first.md), and it is the same absence that makes this register necessary: with no test to encode intent, a written disposition is the only durable record that a gap was seen and answered.

So each row is written to be answerable rather than merely true. It names the observation, cites the line, and commits to one of three decisions. "Noted" is not among them.

## The three dispositions

Each row carries exactly one. They are not interchangeable, and the distinction is what makes the register auditable.

- **migrate** — the behaviour is real and intended. Carry it to the target, corrected. Used where the system does something today that it should keep doing, but does it wrongly, inconsistently or in a form the target cannot express.
- **implement** — the behaviour is absent or non-functional today. Build it properly in the target. Used where the estate declares a capability it never delivered, so there is nothing to carry across and something to construct.
- **drop** — the behaviour is dead, unreachable or unwanted. Do not carry it, and record that the omission is deliberate. Used only where nothing declares the artifact and nothing depends on it, so that a later reader finds a decision rather than an accident.

### The principle that separates implement from drop

Four rows below describe capabilities the estate declares and does not deliver, and one describes a value it displays and gets wrong. They could each be argued either way, so the principle applied to them is stated once here rather than re-argued five times.

**A capability the estate advertises to a user, or guards against in its own code, is a requirement it has failed to deliver — not dead code.** Dropping it silently converts a known gap into an unknown one, which is the exact failure this register exists to prevent. `drop` is therefore reserved for artifacts that nothing declares and nothing depends on. Under that principle the reports menu, the two report layouts, the unreachable status and the two inert command keys are all **implement**, and the superseded company name is **migrate** because it is not inert but wrong. The interdependency between those five rows is set out under [the disposition summary](#disposition-summary).

## Disposition summary

Seventeen entries, seventeen dispositions, and the arithmetic is exact.

| Disposition | Count | Entries |
|---|---|---|
| implement | 9 | DEF-01, DEF-02, DEF-03, DEF-04, DEF-05, DEF-06, DEF-08, DEF-15, DEF-16 |
| migrate | 7 | DEF-07, DEF-10, DEF-11, DEF-12, DEF-13, DEF-14, DEF-17 |
| drop | 1 | DEF-09 |
| **Total** | **17** | 9 + 7 + 1 = 17 |

Two properties of that distribution are worth reading off it. **`implement` is the largest group, and every entry in it is a capability this system declares and does not deliver** — a sweep, its counters, its completion report, a menu option, two report layouts, a contract state, two command keys, a user column and an audit stamp. Nine of seventeen known defects are therefore absences rather than errors, which is a different and more expensive class of finding: an error is visible in the output of the thing that is wrong, whereas an absence is visible only against a statement of what should have been there. **`drop` is the smallest group, and deliberately so.** Only one artifact in the estate is declared by nothing and depended on by nothing.

### Five entries that must be dispositioned together

DEF-04, DEF-05, DEF-06, DEF-08 and DEF-12 are interdependent, and dispositioning them inconsistently would produce a target that contradicts itself. The dependency is concrete rather than thematic.

- Implementing the reports menu (DEF-04) implies producing reports, and the only report specifications the estate has are the two printer files (DEF-05). Dropping the menu option would leave those ten record formats with no consumer in the target either, so DEF-05 would have to be dropped with it.
- The two printer files carry the superseded company name (DEF-12) in their page headings [QDDSSRC/POLRPT.prtf:L16], [QDDSSRC/CLMRPT.prtf:L16]. Reviving the reports means those headings become live output, so the name has to be corrected rather than inherited.
- The unreachable terminated status (DEF-06) and the two inert command keys (DEF-08) are the same kind of finding as the menu option: declared in one member, unhandled in another. Treating one as an undelivered requirement and another as dead code would make the register's own principle unreadable.

All five are therefore dispositioned under the single principle stated above: four are **implement** and DEF-12 is **migrate**, because DEF-12 alone describes something the system actively does and does wrongly, rather than something it fails to do. Had the opposite principle been chosen, all five would move together — the menu option, both report layouts, the terminated state and both command keys would be **drop**, and DEF-12 would reduce to correcting one menu screen. That alternative is coherent; it is not chosen, because it discards a capability the interface advertises to every user without anyone having decided to.

## The nightly job: three entries in one member

`QCLSRC/DLYUPD.clle` is the only scheduled work in the estate and carries three of the seventeen entries. The operational reading of the member — its command sequence, its scheduling and its message vocabulary — is owned by [the operational model](06-operational-model.md); what follows disposes of what that document found.

**DEF-01 — the sweep is a stub.** The member's banner states its purpose: it sweeps the policy master for policies in a grace period, identifies overdue paid-to dates, transitions status through grace to lapsed, and submits the servicing engine for each policy requiring an update [QCLSRC/DLYUPD.clle:L15-L20]. What it contains instead is a single call:

```text
CALL PGM(LIFE400/SVCBILB) PARM('*SWEEP     ' '*DLYUPD     ')
```

That is the whole of the sweep [QCLSRC/DLYUPD.clle:L75]. Two sentinel literals are passed where a policy key and a servicing key are expected, and there is no loop and no cursor anywhere in the member. The program says so itself: the comment immediately above the call records that a full implementation would need a separate driver to read the policy master sequentially and call the servicing engine for each record [QCLSRC/DLYUPD.clle:L65-L69], with a second note repeating that the call should be replaced by a sequential read [QCLSRC/DLYUPD.clle:L73].

The disposition is **implement**, and the reason it is not merely "add a loop" is established in [the operational model](06-operational-model.md) and in [the current-state architecture](02-architecture-current-state.md): every database file in all eight COBOL members is declared for keyed [record-level I/O](../reference/glossary-ibm-i.md#record-level-io) with random access, and a census of all eight finds no positioning operation and no sequential read anywhere. A set-based sweep is not expressible in the current design at all, which is precisely what the member's own comment concedes when it asks for a separate driver program. The target implements the sweep as a set operation; nothing about the present one is carried forward except its intent.

**DEF-02 — the counters never count.** Three counters are declared and initialised to zero: an update count [QCLSRC/DLYUPD.clle:L32], a lapse count [QCLSRC/DLYUPD.clle:L33] and an error count [QCLSRC/DLYUPD.clle:L34]. Only the error count is ever incremented, in the single failure path around the sweep call [QCLSRC/DLYUPD.clle:L77]. Nothing in the member counts a policy, because nothing in the member visits one.

Reference-counting every declared variable in the member — the method and its full result are published in [the operational model](06-operational-model.md) — also shows that **four declarations are their own only occurrence**: a policy key [QCLSRC/DLYUPD.clle:L29], a servicing key [QCLSRC/DLYUPD.clle:L30], the lapse count [QCLSRC/DLYUPD.clle:L33] and a job-log name [QCLSRC/DLYUPD.clle:L37]. The first two are exactly the variables a real iteration would have filled in, which is consistent with the member having been written around a loop that was never added, and it is corroborating evidence for DEF-01 rather than a separate finding.

The row's disposition is **implement**: a sweep that reports how many policies it moved is the observability DEF-01 needs to be trustworthy, and it does not exist today. The four unused declarations are **dropped** as part of that same work — recorded here inside the row rather than as a row of their own, because a declaration with no reader is not a behaviour and there is nothing to decide about it independently.

**DEF-03 — the completion report cannot report.** The count is copied into a character variable prepared to carry it into a message [QCLSRC/DLYUPD.clle:L87], and the completion text is then assembled from the process date and the error count only [QCLSRC/DLYUPD.clle:L88-L89]. The variable holding the count is never referenced again, so the update count does not merely report zero — **it never reaches any message at all**, and the message is sent to both destinations in that state [QCLSRC/DLYUPD.clle:L91], [QCLSRC/DLYUPD.clle:L94]. The error count it does carry can only be incremented by the single catch-all monitor on the sweep call [QCLSRC/DLYUPD.clle:L76-L77].

The consequence is the reason this is a row and not a cosmetic note: a run in which the sweep did nothing useful and a run in which it did everything asked of it produce byte-identical output. The nightly job cannot be used as evidence that the nightly job worked. Disposition **implement** — the target reports the work actually performed, which is the only version of this message that has operational value.

## Declared capabilities that were never delivered

Four entries share one shape: a capability declared in one member and unhandled in another. They are dispositioned together under the principle set out above.

**DEF-04 — the reports menu option.** Option 5 of the main menu moves the message `REPORTS MENU - NOT YET IMPLEMENTED` into the screen's message field and writes it [QCBLLESRC/MAINMENU.cbl:L81]; no program is called. The option sits in the same `EVALUATE` as the four options that do dispatch [QCBLLESRC/MAINMENU.cbl:L73-L79], so it is indistinguishable from them until it is chosen, and the member's banner records the reports menu as an added feature [QCBLLESRC/MAINMENU.cbl:L7]. One detail sharpens it: the banner's own routing list enumerates options 1, 2, 3, 4 and 90 and omits option 5 [QCBLLESRC/MAINMENU.cbl:L10-L15] — the member documents four destinations and offers five choices.

Disposition **implement**. The capability is advertised to every user of the system, and the estate contains its output specification already, which is DEF-05. The dispatch analysis, including why adding a destination is a source change rather than a configuration change, is owned by [the current-state architecture](02-architecture-current-state.md).

**DEF-05 — two report layouts with no producer.** `QDDSSRC/POLRPT.prtf` and `QDDSSRC/CLMRPT.prtf` are complete printer file definitions: five record formats each, and in both cases the five are a full report structure — page heading, column headings, detail line, totals and footer [QDDSSRC/POLRPT.prtf:L15-L64], [QDDSSRC/CLMRPT.prtf:L15-L58]. The build procedure creates both objects [README.md:L153-L154]. A search for both names across all eight COBOL members, all five [CL](../reference/glossary-ibm-i.md#cl-control-language) members and the [copybook](../reference/glossary-ibm-i.md#copybook) returns no reference at all, a result also recorded in [the current-state architecture](02-architecture-current-state.md). Of the 28 record formats the six device members declare between them, these ten have no producer — the count and its breakdown are owned by [the system inventory](01-system-inventory.md).

Disposition **implement**, consistent with DEF-04 by construction: these two members are the specification of the reporting the menu advertises. What is absent is the program between them, and in the target that program is a query rather than the sequential driver this estate cannot express. The format-by-format destination of all 28 formats belongs to [the UI modernization document](../target-state/05-ui-modernization.md).

**DEF-06 — a contract state nothing can enter.** The shared contract declares eight contract-status values as [level-88 condition names](../reference/glossary-ibm-i.md#level-88-condition-name) [QCPYSRC/POLDATA.cpy:L23-L30], one of which is the terminated state [QCPYSRC/POLDATA.cpy:L29]. Searching all eight COBOL members for that literal returns nothing: no statement anywhere assigns it. Yet the condition name is read, in two programs, both of which refuse to service a policy whose status is claimed or terminated [QCBLLESRC/SVCBILB.cbl:L221], [QCBLLESRC/SVCMNT.cbl:L155]. The system guards against a state it cannot reach, and the guards are not dead code — they fire on the claimed half of the same condition.

The transition census that establishes this, and the observation that no expiry transition exists although an expiry date is stored, are owned by [the current data model](04-data-model-current-state.md), whose state diagram draws this state as declared and never entered. Disposition **implement**: two programs depend on the state existing, so it is intended; what was never written is the transition that produces it.

**DEF-08 — two command keys with no handler.** The new-business [display file](../reference/glossary-ibm-i.md#display-file) declares five command keys at file level, before its first record format. Two of them have no handler in the program that reads those screens: a refresh key [QDDSSRC/NBUWDSPF.dspf:L17] and a plan-code prompt key [QDDSSRC/NBUWDSPF.dspf:L20]. The program tests exactly three [indicators](../reference/glossary-ibm-i.md#indicator) — two for exit and cancel and one for issue [QCBLLESRC/NBUWMNT.cbl:L71], [QCBLLESRC/NBUWMNT.cbl:L83] — and a search of the member for the two indicators these keys would set returns nothing.

The two are not equally exposed, and the difference is worth recording because it is the strongest part of the argument for implementing them. The refresh key is **advertised to users** in the repository's own function-key reference [README.md:L242], so a user who presses it has been told it works; the prompt key is declared in DDS and named nowhere else, so no user has been promised anything. Both are nonetheless capabilities the estate declares, and both describe affordances a modern form provides natively — a reset of unsaved input, and a picker over a coded field whose values are a real and small domain. Disposition **implement**, one disposition for the row, and the same principle that governs DEF-04.

## One behavioural divergence, and why it must be settled before conversion

**DEF-07 — a declined application leaves different evidence depending on which path processed it.** The batch program's error paragraph sets the declined contract status [QCBLLESRC/NBUWB.cbl:L507], and that status is persisted: on each of its two validation failures the program performs the error paragraph and immediately rewrites the policy record [QCBLLESRC/NBUWB.cbl:L96-L97], [QCBLLESRC/NBUWB.cbl:L105-L106]. A declined application therefore leaves a stored record saying so.

The online program does something different. On each of its four validation failures it displays the result and leaves the paragraph [QCBLLESRC/NBUWMNT.cbl:L175-L178], and its only write of any kind happens after every validation step has passed [QCBLLESRC/NBUWMNT.cbl:L198-L203]. It never assigns the declined status — a search of all eight members finds that literal in the batch program alone — so the same declined application leaves **no stored trace at all** when it arrives through the interactive path. This is not two spellings of one behaviour; it is two different answers to the question "what happened to that application", and the state-machine reading of it is owned by [the current data model](04-data-model-current-state.md).

The claims domain carries a second instance of the same class, established in detail by [the current-state architecture](02-architecture-current-state.md) and cited here rather than restated. Its exclusion windows are compiled-in literals on the online path and loaded from plan parameters on the batch path, which that document is careful to label **latent** — every plan currently assigns the same value, so no difference is observable today and a single parameter change would activate one. It also records one **active** divergence: the batch path refuses a claim for investigation on a medical-records condition that the online path does not contain at all, so a claim the batch path holds can pass straight through the interactive path. That distinction between latent and active is load-bearing and is not flattened here.

Disposition **migrate**, with one qualification that is the point of the row. Both paths implement a real business outcome, so the behaviour is carried forward — but *which* outcome is correct cannot be determined from the source, because the source is what disagrees. Resolving it is a business decision, and it has to be settled **before** conversion rather than during: a converted implementation necessarily picks one answer, and picking it implicitly, as a side effect of choosing which member to port from, would change behaviour without anyone deciding to. This is also why a divergence of this kind cannot be discovered by a parity comparison alone — a comparison shows that two paths differ, not which is right — and why the behavioural baseline required by [MOD-ADR-008 on characterization tests first](../decisions/MOD-ADR-008-characterization-tests-first.md) must record both behaviours as they stand before either is changed.

## Structural and naming defects

**DEF-09 — an override naming a file its target never opens.** The new-business submitter overrides the claims file to a library-qualified name [QCLSRC/RUNNBUW.clle:L38] and deletes that override afterwards [QCLSRC/RUNNBUW.clle:L54]. The program it submits declares exactly one file, the policy master [QCBLLESRC/NBUWB.cbl:L50-L54]. The override is inert with respect to the work being submitted.

Disposition **drop**, and this is the only **drop** in the register. It qualifies precisely because it fails both halves of the principle: nothing declares a dependency on it, and nothing consumes it. Carrying it forward would fabricate a coupling between new business and claims that does not exist in the code, which is worse than the harmless waste it is today — a spurious dependency in a target is a constraint on how that target can be decomposed.

A related asymmetry across the same family of three submitters is recorded here for the same reason it is not a row of its own: it is a property of the family rather than a defect in any member. Two submitters take the policy key first [QCLSRC/RUNNBUW.clle:L21], [QCLSRC/RUNSVC.clle:L21] and the third takes the claim key first [QCLSRC/RUNCLM.clle:L21]. The third one is not wrong on its own terms — its order matches its target's entry signature exactly [QCBLLESRC/CLMADJB.cbl:L80] — so there is no member to correct. The inconsistency is across the set, and [the operational model](06-operational-model.md) owns both the observation and the reason it matters: a transposed pair of same-length keys is not detectable by the blank-parameter guard that is the only validation these submitters perform. The target exposes one uniform contract, which is the disposition DEF-09 already implies for this family.

**DEF-10 — a record key declared on a group item.** Both programs that open the servicing file declare its record key as the whole servicing section of the shared contract [QCBLLESRC/SVCMNT.cbl:L48], [QCBLLESRC/SVCBILB.cbl:L58] — a group whose first subordinate is a two-character amendment-type code [QCPYSRC/POLDATA.cpy:L117], [QCPYSRC/POLDATA.cpy:L118]. The file itself is keyed on a single service-request identifier [QDDSSRC/SVCPF.pf:L54]. So one side names a composite area beginning with a type code and the other names one identifier.

Two adjacent facts bound what can be concluded, and both are owned by [the current data model](04-data-model-current-state.md): every other record-key declaration in the estate **does** correspond to its file's key — nine declarations across seven programs, keying the policy master and the claims file on real elementary items — and the shared contract contains no item corresponding to the servicing file's key at all, so there was no single item available to name. Disposition **migrate**: the file and the identity of a service request are real and are carried across, with one key stated explicitly, because today the two halves of the declaration disagree about what identifies a record and the schema declares no uniqueness that would settle it. The absent uniqueness and referential integrity are owned by [the current data model](04-data-model-current-state.md); the target key is decided in [the target data model and schema mapping](../target-state/03-target-data-model-and-schema-mapping.md).

**DEF-11 — a duplicated paragraph-number prefix.** The batch claims program carries two paragraphs whose labels both begin `9000-`: an error return [QCBLLESRC/CLMADJB.cbl:L303] and a pending return [QCBLLESRC/CLMADJB.cbl:L311]. The labels are distinct, so this compiles and runs. What breaks is the convention that lets every other program's operation be addressed by its number alone, and [the current-state architecture](02-architecture-current-state.md), which owns the paragraph inventory, records why that matters: rules and tests are anchored by paragraph number, so a duplicated prefix makes one program's anchors ambiguous exactly where behaviour is being captured. Disposition **migrate** — both paragraphs implement wanted behaviour and both are carried across as distinctly named operations.

**DEF-17 — a non-standard qualifier.** One statement in the batch servicing program qualifies a working-storage item with `OF PROCEDURE DIVISION` [QCBLLESRC/SVCBILB.cbl:L372], inside the rider-removal paragraph. A search of the COBOL members and the shared contract finds the form nowhere else in the estate. Disposition **migrate**: the assignment it performs is wanted behaviour and is carried across as a plain assignment, and only the unusual form is discarded. It is a row rather than a footnote because an unexplained idiom is exactly the kind of thing a conversion — automated or manual — mistranslates or silently drops.

## Defects in what the system says about itself

Three entries are not defects in behaviour but in description. They are in the register because a migration team reads descriptions to decide what to do, so an inaccurate description causes incorrect work as surely as an inaccurate program produces incorrect output.

**DEF-12 — a superseded company name on a live screen and two report layouts.** The constant `LINCOLN LIFE INSURANCE CO.` appears in three DDS members: the menu screen [QDDSSRC/MNUDSPF.dspf:L22] and the page heading of each printer file [QDDSSRC/POLRPT.prtf:L16], [QDDSSRC/CLMRPT.prtf:L16]. Every source banner in the estate names a different owner, including the banners of those same three members [QDDSSRC/MNUDSPF.dspf:L4], [QDDSSRC/POLRPT.prtf:L4], [QDDSSRC/CLMRPT.prtf:L4], and so does the repository's own overview [README.md:L3]. The screens and reports therefore display one company while the headers of the very files defining them declare another.

The menu instance is the consequential one, and it is not inert: the menu screen's main record format is written on every iteration of the menu loop, so this name is on the first screen of every session. Disposition **migrate**, one disposition covering all three sites: the corrected name is carried to the target, and the two report sites are included because DEF-05 makes those headings live output again rather than dormant text.

**This row is documented and not corrected.** Correcting three literals in three DDS members would take one edit each and is exactly what the scope boundary of this assessment forbids: no member of `QCBLLESRC/`, `QCLSRC/`, `QCPYSRC/` or `QDDSSRC/` is modified by this documentation set, and this row is named in that boundary as a specific temptation not to act on. The reason is not procedural. These are display and print constants whose field positions are computed by hand in a fixed-format layout, the estate has no test that would catch a mistake, and the correction has no value until the screens and reports are rebuilt in the target anyway. Recording it costs nothing and loses nothing; changing it spends a source edit on an estate that cannot verify one.

**DEF-13 — two inaccurate descriptions of the estate.** Both are documentation-accuracy defects and both are recorded because they would mislead a reader doing real work.

- A superseded source extension. The batch program's rule paragraphs are annotated in the online program as being the same logic as a member named with a `.CBLE` extension [QCBLLESRC/NBUWMNT.cbl:L220], while the working tree uses `.cbl`. This is now the **only** surviving instance of that extension anywhere in the repository: a search of all 24 members returns this one comment, and nothing in `docs/` or the repository overview carries it. The entry-point document did carry it, in the eight entries of its repository-structure diagram, and it **has already been corrected** as part of this deliverable — those entries now name the actual filenames [README.md:L42-L49]. That correction is why every citation in this documentation set can name a `.cbl` path and have it resolve, and it is the single update in a set that is otherwise entirely additive. The in-source instance cannot be corrected on the same terms as DEF-12, so it is recorded instead.
- A consumer list that omits a consumer. The shared contract's banner names the programs that use it, listing six [QCPYSRC/POLDATA.cpy:L12]. Seven programs copy it; the list omits the inquiry program, which copies it [QCBLLESRC/POLMSTINQ.cbl:L50]. [The current data model](04-data-model-current-state.md) owns this observation and states the consequence precisely: anyone using that banner as the impact list for a contract change would miss a consumer, and the missed one is the only read-only program in the estate — the one whose omission is least likely to surface as a compile failure during ordinary work.

Disposition **migrate** for the row: descriptions of the estate are carried forward corrected, one of the three instances is already actioned at the document level, and the two in-source instances are recorded because the member-level boundary holds.

**DEF-14 — six digits against a stated eight.** The repository states a uniform rule: all date fields use eight-digit `YYYYMMDD` [README.md:L258]. One declaration differs. The menu program declares a six-digit date item — the **declaration** is at [QCBLLESRC/MAINMENU.cbl:L47] and the comment describing it is seven lines later at [QCBLLESRC/MAINMENU.cbl:L54], two separate places, which is worth stating because citing one for the other would misdirect a reader to the wrong line. That comment records the item as a display-only date in `MMDDYY` form. It is populated from the system date [QCBLLESRC/MAINMENU.cbl:L55], moved straight to a screen field [QCBLLESRC/MAINMENU.cbl:L56], and that screen field is itself six digits with an edit code [QDDSSRC/MNUDSPF.dspf:L25].

Both positions are recorded and this register does not resolve the disagreement in prose, in agreement with [the current data model](04-data-model-current-state.md), which owns the date inventory and reaches the same reading: the six-digit item belongs to the one program that copies no contract and opens no database file, it is never moved into any contract item and it is never persisted, so the repository's rule holds for every stored date without exception and the exception is a screen field carrying a two-digit year in a system whose stored dates all carry four. Disposition **migrate** — displaying a date is wanted behaviour and is carried across, with one unambiguous representation instead of two. How the eight-digit integers themselves become real dates is decided in [MOD-ADR-006 on date and decimal representation](../decisions/MOD-ADR-006-date-and-decimal-representation.md).

## Attribution defects

Two entries concern who did something. They are separated from the rest because they share a single cause, and because the register's boundary matters most here: the facts are recorded and dispositioned below, while their severity belongs to [the security risk register](../risk/01-security-risk-register.md) and the control that closes them to [the security control design](../target-state/04-security-control-design.md).

**DEF-15 — a user column with no writer.** The servicing file defines a ten-character requesting-user column [QDDSSRC/SVCPF.pf:L51]. It is never populated, and [the current data model](04-data-model-current-state.md) establishes why with a census rather than an inference: the only program that writes the file describes the record as a single undifferentiated two-hundred-byte area [QCBLLESRC/SVCMNT.cbl:L58] and writes that area whole [QCBLLESRC/SVCMNT.cbl:L191], and the name of that record area occurs exactly twice in the entire estate — the declaration and the write. No statement anywhere moves a value into it before it is written. A program writing an undifferentiated area cannot populate an individual column, so the column has no writer at all.

Disposition **implement**. There is nothing to migrate: the column has never held a value, so a data migration has nothing to carry and the capability is new work. The related fact that a signed-on profile *is* available in the estate — captured by the menu program and immediately displayed, then neither persisted nor passed onward [QCBLLESRC/MAINMENU.cbl:L57-L58] — is what makes this an omission rather than an impossibility.

**DEF-16 — the most frequent mutating path stamps nothing.** The interactive servicing program applies an amendment by rewriting the policy master and writing a servicing record, in two consecutive statements [QCBLLESRC/SVCMNT.cbl:L190-L191]. It sets no audit value at all: a search of the member for the contract's audit items returns **zero** occurrences, so neither the user field nor the date field is written on this path. The five other mutating programs each stamp the user field, and each stamps it with its own program name rather than a user identity — [QCBLLESRC/NBUWMNT.cbl:L497], [QCBLLESRC/NBUWB.cbl:L138], [QCBLLESRC/SVCBILB.cbl:L140], [QCBLLESRC/CLMADJB.cbl:L136] and [QCBLLESRC/CLMMNT.cbl:L281].

The consequence is sharper than a missing value, and it is why this row exists separately from DEF-15. The audit column is a fixed-width field on the policy record [QDDSSRC/POLMST.pf:L78], so a rewrite that does not set it preserves whatever was there before. The column therefore retains the **previous** writer's stamp on the most frequent mutating path in the system: the audit trail is not merely weak, it is actively misleading, because it names a program that did not make the change being examined.

A third instance of the same failure sits in the CL layer and is folded in here rather than given a row, because it is the same defect in a different member. The session-entry program retrieves the job's current library [QCLSRC/STRTLIFE.clle:L24] and concatenates it into a message reading `LIFE400 SESSION STARTED BY` [QCLSRC/STRTLIFE.clle:L31] — the text promises a user and carries a library name. [The operational model](06-operational-model.md) owns that observation and the broader finding it belongs to: no user identity is captured anywhere in the CL layer, so no submitter and no scheduled job records who requested the work.

Disposition **implement** — user-attributed audit records, because nothing in the estate captures a user identity into stored data and there is therefore nothing to carry across. One architectural fact is noted and deliberately not pursued: the two writes at [QCBLLESRC/SVCMNT.cbl:L190-L191] are not atomic, and a search of all COBOL and CL members finds no commitment or rollback operation anywhere. That is recorded here only to explain why the audit gap and the atomicity gap are visible at the same two lines; its severity belongs to [the security risk register](../risk/01-security-risk-register.md) and its recovery consequences to [the continuity and recovery risk document](../risk/03-continuity-and-recovery-risk.md).
