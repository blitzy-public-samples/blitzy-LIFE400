# LIFE400 Known Defects, Stubs and Inert Features

This document is the disposition register for the LIFE400 estate. It collects every defect, stub, inert feature and internal contradiction that the current-state layer established with evidence, and it assigns each one exactly one decision: **migrate**, **implement** or **drop**. Seventeen entries are recorded, identified `DEF-01` through `DEF-17`, and each carries the source line that establishes it. This is the last document in the layer and the only one that decides anything: documents one through six state what is true, and this one states what is to become of it.

**Scope.** This register decides dispositions and stops there. It assigns no severity and designs no control — anything security-relevant below is registered for severity in [the security risk register](../risk/01-security-risk-register.md) and closed by a control in [the security control design](../target-state/04-security-control-design.md). It performs no continuity analysis: atomicity, recovery objectives and reconciliation belong to [the continuity and recovery risk document](../risk/03-continuity-and-recovery-risk.md). It publishes no target column, type or constraint — that is [the target data model and schema mapping](../target-state/03-target-data-model-and-schema-mapping.md) — and no target screen or route, which is [the UI modernization document](../target-state/05-ui-modernization.md). It restates no schema, no [paragraph](../reference/glossary-ibm-i.md#paragraph) inventory and no rule census; each of those has one owning document, cited where it is used. A disposition here is a decision about a known fact, not a design.

**Reading the citations.** Every claim carries an inline citation of the form `[<path>:<locator>]` immediately after the claim. Citations are plain text and deliberately not hyperlinks: a plain-text citation stays meaningful in a diff and does not depend on a hosting provider's line-anchor syntax. Open the member to read the statement in place. Platform terms link to [the IBM i glossary](../reference/glossary-ibm-i.md) on first use in this document.

**Nothing here was fixed.** This is a register of observations and recommendations, and every one of the 24 members is left exactly as it stands. No source member is annotated, corrected, reformatted or commented by this documentation set, and the machine-generated corpus under `.swm/` is neither edited nor reproduced. Three entries below are especially easy to misread as invitations to edit — a superseded company name on a live screen, a stale filename in a source comment, and a spurious file [override](../reference/glossary-ibm-i.md#override) — and none of them is touched. The correction each row proposes is a target-side action, recorded so that it happens deliberately and once, in the target, rather than opportunistically in an estate that has no test suite to catch a mistake.

**How this register was assembled.** Each entry began as an observation published by one of the six preceding documents, which state facts and explicitly defer disposition here. Every anchor was then re-verified by opening the member and confirming that the cited line holds the construct claimed, because a citation that resolves to a real line but points at the wrong statement is worse than no citation: it survives every automated check and misleads every reader. Absence claims — that no program names a [printer file](../reference/glossary-ibm-i.md#printer-file), that no statement assigns a status, that no handler exists for a command key — were established by searching all 24 members rather than by inspecting the places the behaviour was expected. Where two parts of the system disagree, both positions are recorded and the disagreement itself is the entry; this register does not silently pick a winner and then document the winner as fact.

## Why a register, and why every row forces a decision

A defect carried forward silently becomes a defect in the target. A stub carried forward silently becomes a missing feature discovered after cutover, when the system that used to be a reference is gone. Both failures share one cause: an observation that stayed an observation. This system offers unusually many opportunities for that. A nightly job whose sweep is a placeholder still completes successfully every run. A menu option that reports its own absence still appears to every user. Two report layouts that no program produces still exist as compiled objects. A status value that nothing can assign is still guarded against in two programs. Each of those reads, at a glance, like working software.

The estate also offers no safety net that would catch the omission later. The repository's structure diagram enumerates every directory and every member it holds — the four source directories, the 8 COBOL programs, the 5 CL programs, the copybook and the 10 DDS members [README.md:L27-L55] — and not one of them is a test member or a test-runner configuration; the documented build is eight steps of platform commands with no test step among them [README.md:L120-L218]. So nothing fails when a behaviour quietly disappears, and no build step compares the estate against a description of itself. That absence is why conversion is gated on a behavioural baseline in [MOD-ADR-008 on characterization tests first](../decisions/MOD-ADR-008-characterization-tests-first.md), and it is the same absence that makes this register necessary: with no test to encode intent, a written disposition is the only durable record that a gap was seen and answered.

So each row is written to be answerable rather than merely true. It names the observation, cites the line, and commits to one of three decisions. "Noted" is not among them.

## The three dispositions

Each row carries exactly one. They are not interchangeable, and the distinction is what makes the register auditable.

- **migrate** — the behaviour is real and intended. Carry it to the target, corrected. Used where the system does something today that it should keep doing, but does it wrongly, inconsistently or in a form the target cannot express.
- **implement** — the behaviour is absent or non-functional today. Build it properly in the target. Used where the estate declares a capability it never delivered, so there is nothing to carry across and something to construct.
- **drop** — the behaviour is dead, unreachable or unwanted. Do not carry it, and record that the omission is deliberate. Used only where nothing declares the artifact and nothing depends on it, so that a later reader finds a decision rather than an accident. Exactly one row below carries this disposition, DEF-09 — a file redirection whose target program declares no such file [QCLSRC/RUNNBUW.clle:L38], [QCBLLESRC/NBUWB.cbl:L50-L54] — and the reason only one does is set out under [the disposition summary](#disposition-summary).

### The principle that separates implement from drop

Three rows below describe capabilities the estate declares and does not deliver, and one describes a value it displays and gets wrong. They could each be argued either way, so the principle applied to them is stated once here rather than re-argued four times.

**A capability the estate advertises to a user, or guards against in its own code, is a requirement it has failed to deliver — not dead code.** The reports option is offered on the menu screen every session displays [QCBLLESRC/MAINMENU.cbl:L81], the refresh key is published as a common function key [README.md:L242], and the terminated contract state is guarded against in two programs [QCBLLESRC/SVCBILB.cbl:L221], [QCBLLESRC/SVCMNT.cbl:L155]. Dropping such a thing silently converts a known gap into an unknown one, which is the exact failure this register exists to prevent. `drop` is therefore reserved for artifacts that nothing declares and nothing depends on. Under that principle the reporting capability with its two layouts, the unreachable status and the unhandled command keys are all **implement**, and the superseded company name is **migrate** because it is not inert but wrong. The interdependency between those four rows is set out under [the disposition summary](#disposition-summary).

## Disposition summary

Seventeen entries, seventeen dispositions, and the arithmetic is exact.

| Disposition | Count | Entries |
|---|---|---|
| implement | 8 | DEF-01, DEF-02, DEF-03, DEF-04, DEF-06, DEF-08, DEF-15, DEF-16 |
| migrate | 8 | DEF-05, DEF-07, DEF-10, DEF-11, DEF-12, DEF-13, DEF-14, DEF-17 |
| drop | 1 | DEF-09 |
| **Total** | **17** | 8 + 8 + 1 = 17 |

Two properties of that distribution are worth reading off it. **`implement` and `migrate` are the same size, and they divide the register almost exactly in half along one line: absence against error.** Every `implement` entry is a capability this system declares and does not deliver — a sweep, its telemetry, batch work that can actually run and bind its files, a reporting capability with its layouts, a contract state, a screen bound to its own fields, two secondary files with real columns, and an audit trail. Every `migrate` entry is behaviour the system performs and performs wrongly: rules computing on values their fields cannot hold, two paths of a domain answering differently, keys naming items their file does not describe, a duplicated paragraph prefix, a superseded company name, two inaccurate self-descriptions, dates that are numbers, and statements in forms the language does not define. The distinction is not cosmetic — an error is visible in the output of the thing that is wrong, whereas an absence is visible only against a statement of what should have been there, which is why eight of these seventeen would survive any amount of output comparison.

**Exactly one row is a `drop`, and the scarcity of that disposition is itself a finding about the estate.** The disposition exists for artifacts that nothing declares and nothing depends on, and only DEF-09 qualifies: a single redundant file redirection naming a file its target program never opens. Everything else this system leaves unreachable, inert or contradictory is something it also declares somewhere — advertised on a screen, guarded against in code, or created by the build — which is precisely why it cannot be discarded silently.

### Four entries that must be dispositioned together

DEF-04, DEF-06, DEF-08 and DEF-12 are interdependent, and dispositioning them inconsistently would produce a target that contradicts itself. The dependency is concrete rather than thematic.

- The reports menu option and the two report layouts are one row (DEF-04) precisely because neither half stands alone: implementing the option implies producing reports, and the only report specifications the estate has are those two printer files. Dropping the option would leave those ten record formats with no consumer in the target either, so the whole row would move together.
- The two printer files carry the superseded company name (DEF-12) in their page headings [QDDSSRC/POLRPT.prtf:L16], [QDDSSRC/CLMRPT.prtf:L16]. Reviving the reports means those headings become live output, so the name has to be corrected rather than inherited.
- The unreachable terminated status (DEF-06) and the unbound screens with their unhandled command keys (DEF-08) are the same kind of finding as the menu option: declared in one member, unhandled in another. Treating one as an undelivered requirement and another as dead code would make the register's own principle unreadable.

All four are therefore dispositioned under the single principle stated above: three are **implement** and DEF-12 is **migrate**, because DEF-12 alone describes something the system actively does and does wrongly, rather than something it fails to do. Had the opposite principle been chosen, all four would move together — the menu option with both report layouts, the terminated state and the unhandled keys would be **drop**, and DEF-12 would reduce to correcting one menu screen. That alternative is coherent; it is not chosen, because it discards a capability the interface advertises to every user without anyone having decided to.

## The batch layer: three entries

`QCLSRC/DLYUPD.clle` is the only scheduled work in the estate — it carries the single scheduling command in its own banner [QCLSRC/DLYUPD.clle:L12-L13] and the build procedure issues that command once and for no other program [README.md:L209-L211] — and it anchors the first two entries — the second of which reaches beyond this member, because the requester-notification half of it appears in the three submitters as well — while the third belongs to the batch layer as a whole, the three submitters and the nightly member together. The operational reading of all four members — their command sequences, their scheduling and their message vocabulary — is owned by [the operational model](06-operational-model.md); what follows disposes of what that document found.

**DEF-01 — the sweep is a stub.** The member's banner states its purpose: it sweeps the policy master for policies in a grace period, identifies overdue paid-to dates, transitions status through grace to lapsed, and submits the servicing engine for each policy requiring an update [QCLSRC/DLYUPD.clle:L15-L20]. What it contains instead is a single call:

```text
CALL PGM(LIFE400/SVCBILB) PARM('*SWEEP     ' '*DLYUPD     ')
```

That is the whole of the sweep [QCLSRC/DLYUPD.clle:L75]. Two sentinel literals are passed where a policy key and a servicing key are expected, and there is no loop and no cursor anywhere in the member. The program says so itself: the comment immediately above the call records that a full implementation would need a separate driver to read the policy master sequentially and call the servicing engine for each record [QCLSRC/DLYUPD.clle:L65-L69], with a second note repeating that the call should be replaced by a sequential read [QCLSRC/DLYUPD.clle:L73].

The disposition is **implement**, and the reason it is not merely "add a loop" is established in [the operational model](06-operational-model.md) and in [the current-state architecture](02-architecture-current-state.md): every database file in all eight COBOL members is declared for keyed [record-level I/O](../reference/glossary-ibm-i.md#record-level-io) with random access, and a census of all eight finds no positioning operation and no sequential read anywhere. A set-based sweep is not expressible in the current design at all, which is precisely what the member's own comment concedes when it asks for a separate driver program. The target implements the sweep as a set operation; nothing about the present one is carried forward except its intent.

**DEF-02 — the notification channel cannot report what the work did, and two of its commands cannot be shown to deliver at all.** Three counters are declared and initialised to zero: an update count [QCLSRC/DLYUPD.clle:L32], a lapse count [QCLSRC/DLYUPD.clle:L33] and an error count [QCLSRC/DLYUPD.clle:L34]. Only the error count is ever incremented, in the single failure path around the sweep call [QCLSRC/DLYUPD.clle:L77]. Nothing in the member counts a policy, because nothing in the member visits one.

Reference-counting every declared variable in the member — the method and its full result are published in [the operational model](06-operational-model.md) — also shows that **four declarations are their own only occurrence**: a policy key [QCLSRC/DLYUPD.clle:L29], a servicing key [QCLSRC/DLYUPD.clle:L30], the lapse count [QCLSRC/DLYUPD.clle:L33] and a job-log name [QCLSRC/DLYUPD.clle:L37]. The first two are exactly the variables a real iteration would have filled in, which is consistent with the member having been written around a loop that was never added, and it is corroborating evidence for DEF-01 rather than a separate finding.

The second half of the same row is the message. The update count is copied into a character variable prepared to carry it [QCLSRC/DLYUPD.clle:L87], and the completion text is then assembled from the process date and the error count only [QCLSRC/DLYUPD.clle:L88-L89]. The variable holding the count is never referenced again, so the update count does not merely report zero — **it never reaches any message at all**, and the message is sent to both destinations in that state [QCLSRC/DLYUPD.clle:L91], [QCLSRC/DLYUPD.clle:L94]. The error count it does carry can only be incremented by the single catch-all monitor on the sweep call [QCLSRC/DLYUPD.clle:L76-L77].

Counting and reporting belong in one row rather than two because neither half is worth anything without the other: a counter that counts and a message that omits it leaves the same silence, and a message that reports a counter nothing increments reports zero forever. The consequence is why this is a row and not a cosmetic note: a run in which the sweep did nothing useful and a run in which it did everything asked of it produce byte-identical output, so the nightly job cannot be used as evidence that the nightly job worked. Disposition **implement**: the target counts the work and reports what it counted, which is the observability DEF-01 needs to be trustworthy and does not exist in either half today. The four unused declarations — a policy key [QCLSRC/DLYUPD.clle:L29], a servicing key [QCLSRC/DLYUPD.clle:L30], the lapse count and a job-log name [QCLSRC/DLYUPD.clle:L37] — are **dropped** as part of that same work, recorded inside the row rather than as a row of their own, because a declaration with no reader is not a behaviour and there is nothing to decide about it independently.

The same row carries two further failures of the same channel, because both are the notification layer declaring a destination it does not reach, and one decision covers all three. **The sweep-failure diagnostic pairs a message type with a destination that type does not address.** When the monitored condition around the sweep call fires, the member increments its error count and sends a diagnostic naming a message queue object [QCLSRC/DLYUPD.clle:L78-L80]; a diagnostic message type is defined against a call message queue rather than a named queue, so the type and the destination in that one command are not a pair the command supports. The same member's informational messages to the same queue carry no such problem [QCLSRC/DLYUPD.clle:L53], [QCLSRC/DLYUPD.clle:L95], which is what makes this a defect in one command rather than a property of the queue. **And all three batch submitters address their requester notification with a keyword that does not offer that destination** [QCLSRC/RUNNBUW.clle:L49-L50], [QCLSRC/RUNSVC.clle:L56-L57], [QCLSRC/RUNCLM.clle:L56-L57]; the keyword definitions and the exact mismatch are established by [the operational model](06-operational-model.md). Neither can be settled by running anything, because nothing in this repository can be compiled or executed, so both are recorded as what the source specifies rather than as observed behaviour.

Disposition **implement**, covering the counting, the completion text and both invalid destinations together — the target counts the work actually performed, reports it, reports its failures where a reader will see them, and returns something to the caller that asked for the work. That is one design decision about one channel, which is why it is one row.

**DEF-03 — submitted batch work is not set up to run.** This entry is the batch layer's counterpart to DEF-01: where the nightly job declares an iteration it does not perform, the three submitters declare a binding they cannot deliver. Four facts establish it, each owned by [the operational model](06-operational-model.md) and cited here rather than re-derived.

- **Six file redirections are issued in the wrong job.** Each submitter issues two `OVRDBF … OVRSCOPE(*JOB)` commands before submitting — [QCLSRC/RUNNBUW.clle:L37-L38], [QCLSRC/RUNSVC.clle:L44-L45], [QCLSRC/RUNCLM.clle:L44-L45] — and the scope keyword names the job that runs the command. [`SBMJOB`](../reference/glossary-ibm-i.md#sbmjob) then starts a different job [QCLSRC/RUNNBUW.clle:L43], and the submitter deletes its own redirections a few lines later. The batch program resolves its unqualified file names on its own.
- **Nothing gives the submitted job a library list.** The job description every submission names is created with a queue and a text description and nothing else [README.md:L199], and no submission passes a library-list or current-library parameter [QCLSRC/RUNNBUW.clle:L43-L46]. The only two commands in the estate that put the application library on a list run in the interactive session [QCLSRC/STRTLIFE.clle:L27] and in the nightly job's own job [QCLSRC/DLYUPD.clle:L56].
- **Nothing attaches the job queue to a subsystem.** A census of the whole repository for a job-queue entry, a subsystem description, a routing entry or a subsystem start returns no match, so this repository establishes where every asynchronous request is sent and does not establish that any of it is selected to run.
- **The cleanup that follows is guarded one command too late.** Each of the four members with overrides issues two deletions and then a single monitored condition — [QCLSRC/RUNNBUW.clle:L53-L55], [QCLSRC/RUNSVC.clle:L60-L62], [QCLSRC/RUNCLM.clle:L60-L62], [QCLSRC/DLYUPD.clle:L98-L100] — and a monitor written after a command covers that command. So the first deletion is unguarded, and the case it would fail on is exactly the case the monitor anticipates: an override already absent. When it happens the second deletion does not run, and in the nightly job the library-list removal that follows it [QCLSRC/DLYUPD.clle:L102] does not run either.

Disposition **implement**. Asynchronous batch work is real and intended — it is the estate's only asynchrony mechanism — but as configured the repository does not establish that a submitted job runs, or that it opens the files the submitter meant it to. The target supplies the binding and the queue attachment explicitly, and a cleanup that cannot be interrupted by the condition it exists to tolerate. Two boundaries are worth stating. Five of the six redirections name files their target really does open, the exception being the one DEF-09 records, so this is a placement defect rather than a fabricated dependency and the two rows are not the same finding. And the nightly job's own redirections do take effect, because the program it calls runs synchronously in the job that issued them [QCLSRC/DLYUPD.clle:L75] — which is what makes the submitters' placement, rather than the commands themselves, the defect.

## Declared capabilities that were never delivered

Three entries share one shape: a capability declared in one member and unhandled in another. They are dispositioned together under the principle set out above.

**DEF-04 — a reporting capability declared at both ends.** The row has two halves and they are one entry because neither is a finding without the other.

The first half is the menu option. Option 5 of the main menu moves the message `REPORTS MENU - NOT YET IMPLEMENTED` into the screen's message field and writes it [QCBLLESRC/MAINMENU.cbl:L81]; no program is called. The option sits in the same `EVALUATE` as the four options that do dispatch [QCBLLESRC/MAINMENU.cbl:L73-L79], so it is indistinguishable from them until it is chosen, and the member's banner records the reports menu as an added feature [QCBLLESRC/MAINMENU.cbl:L7]. One detail sharpens it: the banner's own routing list enumerates options 1, 2, 3, 4 and 90 and omits option 5 [QCBLLESRC/MAINMENU.cbl:L10-L15] — the member documents four destinations and offers five choices.

The second half is the output specification the option would need. `QDDSSRC/POLRPT.prtf` and `QDDSSRC/CLMRPT.prtf` are complete printer file definitions: five record formats each, and in both cases the five are a full report structure — page heading, column headings, detail line, totals and footer [QDDSSRC/POLRPT.prtf:L15-L64], [QDDSSRC/CLMRPT.prtf:L15-L58]. The build procedure creates both objects [README.md:L153-L154]. A search for both names across all eight COBOL members, all five [CL](../reference/glossary-ibm-i.md#cl-control-language) members and the [copybook](../reference/glossary-ibm-i.md#copybook) returns no reference at all, a result also recorded in [the current-state architecture](02-architecture-current-state.md). Of the 28 record formats the six device members declare between them, these ten have no producer — the count and its breakdown are owned by [the system inventory](01-system-inventory.md).

Disposition **implement**, one disposition for both halves. The capability is advertised to every user of the system and its output is already specified; what is absent is the program between the two, and in the target that program is a query rather than the sequential driver this estate cannot express. Dropping either half would force dropping the other, which is the interdependency recorded under the summary above. The dispatch analysis, including why adding a destination is a source change rather than a configuration change, is owned by [the current-state architecture](02-architecture-current-state.md); the format-by-format destination of all 28 formats belongs to [the UI modernization document](../target-state/05-ui-modernization.md).

**DEF-06 — a contract state nothing can enter.** The shared contract declares eight contract-status values as [level-88 condition names](../reference/glossary-ibm-i.md#level-88-condition-name) [QCPYSRC/POLDATA.cpy:L23-L30], one of which is the terminated state [QCPYSRC/POLDATA.cpy:L29]. Searching all eight COBOL members for that literal returns nothing: no statement anywhere assigns it. Yet the condition name is read, in two programs, both of which refuse to service a policy whose status is claimed or terminated [QCBLLESRC/SVCBILB.cbl:L221], [QCBLLESRC/SVCMNT.cbl:L155]. The system guards against a state it cannot reach, and the guards are not dead code — they fire on the claimed half of the same condition.

The transition census that establishes this, and the observation that no expiry transition exists although an expiry date is stored, are owned by [the current data model](04-data-model-current-state.md), whose state diagram draws this state as declared and never entered. Disposition **implement**: two programs depend on the state existing, so it is intended; what was never written is the transition that produces it.

**DEF-08 — screens that are not bound to the programs that drive them.** Two findings of the same kind sit in this row: keys the file declares and the program never handles, and fields the program uses and nothing declares.

The new-business [display file](../reference/glossary-ibm-i.md#display-file) declares five command keys at file level, before its first record format. Two of them have no handler in the program that reads those screens: a refresh key [QDDSSRC/NBUWDSPF.dspf:L17] and a plan-code prompt key [QDDSSRC/NBUWDSPF.dspf:L20]. The program tests exactly three [indicators](../reference/glossary-ibm-i.md#indicator) — two for exit and cancel and one for issue [QCBLLESRC/NBUWMNT.cbl:L71], [QCBLLESRC/NBUWMNT.cbl:L83] — and a search of the member for the two indicators these keys would set returns nothing.

The second finding is the wider one and runs the other way. All four interactive programs declare their display file as a program-described area of eighty characters — the menu is the shortest illustration, with its file declared at [QCBLLESRC/MAINMENU.cbl:L32-L36] and its record at [QCBLLESRC/MAINMENU.cbl:L40-L41] — and then move values into named DDS fields and branch on native indicators that nothing in the program defines. The menu's entire working storage is five items [QCBLLESRC/MAINMENU.cbl:L44-L48], none of them a screen field, yet it writes a date and a user into two screen fields [QCBLLESRC/MAINMENU.cbl:L56], [QCBLLESRC/MAINMENU.cbl:L58], reads a selection back out of a third [QCBLLESRC/MAINMENU.cbl:L70] and branches on two indicators [QCBLLESRC/MAINMENU.cbl:L65], [QCBLLESRC/MAINMENU.cbl:L67]. A census of all eight members finds no indicator clause, no externally-described file declaration and no copy of a DDS field list anywhere; [the current-state architecture](02-architecture-current-state.md) owns the per-program field and indicator sets and records this among the constructs that stand between the estate and a successful compile.

The two command keys are not equally exposed, and the difference is the strongest part of the argument for implementing rather than dropping. The refresh key is **advertised to users** in the repository's own function-key reference [README.md:L242], so a user who presses it has been told it works; the prompt key is declared in DDS and named nowhere else, so no user has been promised anything. Both are capabilities the estate declares, and both describe affordances a modern form provides natively — a reset of unsaved input, and a picker over a coded field whose values are a real and small domain. Disposition **implement**, one disposition for the row and the same principle that governs DEF-04: the target builds each form together with the bindings between it and its handler, which is precisely what this estate declares in two places and joins in neither.

## The divergences between each domain's two paths

**DEF-07 — each domain is implemented twice, and each pair answers differently in its own way.** The complete inventory of those differences — every one found by reading both bodies of each pair, with both sides cited and each classified active, latent or inert — is owned by [the current-state architecture](02-architecture-current-state.md), and no count from it is restated here. What this row adds is a disposition, and the reason it is a single row is that every family below fails for the same reason and has to be answered the same way. The five families, and what each commits the target to:

- **Session state carries between transactions on the online path.** The batch new-business program resets its accumulators, its outcome pair and both referral flags before validating anything [QCBLLESRC/NBUWB.cbl:L122-L139]; the online program has no such paragraph and re-enters its issue coordinator with the previous application's state intact [QCBLLESRC/NBUWMNT.cbl:L166]. A stale outcome code rejects the next application before it is validated, and both referral flags latch once set. **Disposition for the family: migrate as the batch behaviour** — per-transaction initialisation is the behaviour that is correct on its own terms, and no business decision is needed to prefer it, which makes this the one family that can be settled from the source.
- **A declined application leaves different evidence depending on which path processed it.** The batch error paragraph sets the declined contract status [QCBLLESRC/NBUWB.cbl:L507] and the driver rewrites the record on each validation failure [QCBLLESRC/NBUWB.cbl:L96-L97], [QCBLLESRC/NBUWB.cbl:L105-L106]. The online program displays the result and leaves the paragraph [QCBLLESRC/NBUWMNT.cbl:L175-L178], writes only after every check has passed [QCBLLESRC/NBUWMNT.cbl:L198-L203], and never assigns that status at all — a search of all eight members finds the literal in the batch program alone. So the same declined application leaves a stored record on one path and **no stored trace at all** on the other. **Disposition: migrate, business decision first** — this is two answers to "what happened to that application", and the source cannot arbitrate. The state-machine reading is owned by [the current data model](04-data-model-current-state.md).
- **Servicing rules exist on one path and not the other.** The batch dispatcher accepts an unrecognised amendment type where the online path rejects it [QCBLLESRC/SVCBILB.cbl:L113-L120] against [QCBLLESRC/SVCMNT.cbl:L186-L188]; the third plan's remaining-term refusal and the overdue-premium accrual exist only in batch; and the two paths reprice different sets of riders. **Disposition: migrate the union, rule by rule** — each absent rule is either wanted on both paths or wanted on neither, and that is a business decision per rule rather than one decision for the family. The unrecognised-type case is the exception: accepting an unmatched type and then reporting success is not a candidate behaviour, so it is carried as the online path's rejection.
- **Claims paths decide alike and differ in what they report and persist.** The batch path rewrites the master on four separate paths where the online path writes only after settlement [QCBLLESRC/CLMADJB.cbl:L100] against [QCBLLESRC/CLMMNT.cbl:L178-L179]; one path sets an explanatory message where the other leaves the message it found; the settled batch path never sets the outcome code its own return paragraphs set; and the audit stamp is written on every batch path but only on the settled online path. **Disposition: migrate as one persistence and reporting contract** — the target records the same outcome for the same decision regardless of how the request arrived, which is the one property no version of the current pair has.
- **Windows are compiled in on one path and parameterised on the other.** The reinstatement, contestability and suicide windows are compiled-in literals on the online path [QCBLLESRC/CLMMNT.cbl:L210-L227] and loaded from plan parameters on the batch path [QCBLLESRC/CLMADJB.cbl:L142-L163], [QCBLLESRC/CLMADJB.cbl:L201-L230], and every plan currently loads the value the literal already holds — the architecture document labels these **latent** for exactly that reason. **Disposition: migrate as parameters** — a plan term belongs to the plan, and this is the family a parity comparison is least able to help with, because no comparison of current outputs would show a difference at all.

One further difference is classified **inert** rather than latent or active: the batch document check overwrites its own outcome code with the value the online path sets directly, so the paths agree and the overwritten code is unreachable in the estate. It is dispositioned inside this row as **drop the unreachable code, migrate the behaviour** — the target does not define an outcome nothing can produce.

Disposition for the row: **migrate**, with the qualification that is the point of it. Every family implements real business outcomes, so the behaviour is carried forward — as one implementation per domain — but for three of the five families *which* answer is correct cannot be determined from the source, because the source is what disagrees. Resolving those is a business decision, and it has to be settled **before** conversion rather than during: a converted implementation necessarily picks one answer, and picking it implicitly, as a side effect of choosing which member to port from, would change behaviour without anyone deciding to. This is also why divergence of this kind cannot be discovered by a parity comparison alone — a comparison shows that two paths differ, not which is right, and for the latent family it shows nothing at all — and why the behavioural baseline required by [MOD-ADR-008 on characterization tests first](../decisions/MOD-ADR-008-characterization-tests-first.md) must record both behaviours as they stand before either is changed. The per-rule entries that carry these families into the acceptance oracle are specified by [the business rule inventory](05-business-rule-inventory.md).

## Numeric and input representation

**DEF-05 — the rules compute on values their fields cannot hold, and on an input nothing supplies.** Four facts, each verified in source and each changing a result the rules produce. The field-level analysis is owned by [the current data model](04-data-model-current-state.md) and the consequences for assertions by [the business rule inventory](05-business-rule-inventory.md); what follows is what becomes of them.

- **The plan's monetary bounds do not survive being loaded.** Each plan branch moves fourteen-digit literals into the bound fields [QCBLLESRC/NBUWB.cbl:L149-L150], [QCBLLESRC/NBUWB.cbl:L163-L164], [QCBLLESRC/NBUWB.cbl:L177-L178], and those fields are declared with thirteen integer digits [QCPYSRC/POLDATA.cpy:L42-L43]. The sum-assured validation rule then tests against whatever survived [QCBLLESRC/NBUWB.cbl:L239-L240], so the bounds it enforces are not the bounds the product table publishes [README.md:L62-L66], and the same literals appear in the online twin [QCBLLESRC/NBUWMNT.cbl:L226-L268].
- **The reinsurance referral cannot fire.** It compares the sum assured against a literal larger than the sum-assured field can represent [QCBLLESRC/NBUWB.cbl:L471], and the online twin carries the same comparison [QCBLLESRC/NBUWMNT.cbl:L474].
- **A claim amount that cannot be negative is tested for being negative.** The payment amount is unsigned [QCPYSRC/POLDATA.cpy:L169] and the settlement logic decrements it and then tests it against zero from below [QCBLLESRC/CLMADJB.cbl:L281], [QCBLLESRC/CLMMNT.cbl:L266]. Only one monetary item in the whole contract is signed [QCPYSRC/POLDATA.cpy:L106].
- **The age every rating decision reads is supplied by nothing.** The issue age [QCPYSRC/POLDATA.cpy:L58] is the receiving field of no statement in any member, and no screen collects it: the underwriting display file has a date-of-birth field [QDDSSRC/NBUWDSPF.dspf:L57] and no age field, and the one program that reads that field moves it into the contract's date of birth [QCBLLESRC/NBUWMNT.cbl:L115], which nothing then reads. Both the age bounds and the third plan's term derivation [QCBLLESRC/NBUWB.cbl:L187-L188] rest on it.

Disposition **migrate**. Underwriting, rating and settlement are real, intended, business-critical behaviour and are carried forward — with fields wide enough for the published product values, a referral threshold that can fire, an amount that is either signed or floored deliberately, and an issue age the target captures rather than assumes. The row is **migrate** rather than **implement** because the behaviour exists and is wrong, not absent; the one absence inside it, capturing the age, is built as part of carrying the rating rules across rather than dispositioned separately, in the same way DEF-02 drops its unused declarations inside its own row. What this row does **not** decide is the target's numeric types: exact decimal representation and the treatment of dates are decided once, in [MOD-ADR-006 on date and decimal representation](../decisions/MOD-ADR-006-date-and-decimal-representation.md).

## Structural and naming defects

**DEF-09 — a file redirection for a file the submitted program never opens.** The new-business submitter redirects two files to library-qualified names at job scope immediately before submitting its batch job — the policy master [QCLSRC/RUNNBUW.clle:L37] and the claims file [QCLSRC/RUNNBUW.clle:L38] — and deletes both redirections afterwards [QCLSRC/RUNNBUW.clle:L53], [QCLSRC/RUNNBUW.clle:L54]. The program it submits declares exactly one file, the policy master [QCBLLESRC/NBUWB.cbl:L50-L54], and a search of the member for the claims file returns nothing: no `SELECT`, no file description and no statement names it. The second redirection is therefore for a file that would not be opened even if the redirection reached the job.

Disposition **drop**, and this is the only row in the register that carries it. The test for `drop` is that nothing declares the artifact and nothing depends on it, and this one meets the test exactly: the override is the sole mention of the claims file anywhere in the new-business path, so there is no behaviour to carry across and nothing for the target to replace it with. Carrying it forward would fabricate a coupling between new business and claims that does not exist in the code, and a spurious dependency in a target is a constraint on how that target can be decomposed — it would imply that issuing a policy needs access to claims data.

**A wider property of all six submitter overrides, folded in here rather than made a row of its own.** Each of the three submitters issues two overrides at job scope and then *submits* rather than calls [QCLSRC/RUNNBUW.clle:L37-L38], [QCLSRC/RUNSVC.clle:L44-L45], [QCLSRC/RUNCLM.clle:L44-L45] against [QCLSRC/RUNNBUW.clle:L43-L46], [QCLSRC/RUNSVC.clle:L50-L53], [QCLSRC/RUNCLM.clle:L50-L53], so each pair binds the submitter's own job and not the job being submitted, and what resolves a batch program's unqualified file declarations [QCBLLESRC/NBUWB.cbl:L50-L54] is the library list the submitted job inherits from its caller — normally put in place by the session entry program [QCLSRC/STRTLIFE.clle:L27]. The nightly driver is the contrast: its overrides *do* bind, because it calls its program in the same job [QCLSRC/DLYUPD.clle:L75]. [The operational model](06-operational-model.md) owns that mechanism and its two failure modes — an open that fails because the application library is absent, and an open that succeeds against the wrong library and silently processes the wrong data. It is context here rather than an eighteenth row because a register row is an artifact to migrate, implement or drop, whereas this is a property of where six commands sit relative to a submission; the target requirement it implies — that a unit of batch work states its own data binding rather than inheriting its caller's resolution — is part of the externalized-configuration requirement owned by [the target architecture](../target-state/01-target-architecture.md).

A related asymmetry across the same family of three submitters is recorded here for the same reason: it is a property of the family rather than a defect in any member. Two submitters take the policy key first [QCLSRC/RUNNBUW.clle:L21], [QCLSRC/RUNSVC.clle:L21] and the third takes the claim key first [QCLSRC/RUNCLM.clle:L21]. The third one is not wrong on its own terms — its order matches its target's entry signature exactly [QCBLLESRC/CLMADJB.cbl:L80] — so there is no member to correct. The inconsistency is across the set, and [the operational model](06-operational-model.md) owns both the observation and the reason it matters: a transposed pair of same-length keys is not detectable by the blank-parameter guard that is the only validation these submitters perform [QCLSRC/RUNCLM.clle:L29], [QCLSRC/RUNCLM.clle:L36]. One uniform contract for requesting batch work in the target answers both this and the binding property above, because a request that names its own parameters explicitly has to name its own data binding the same way.

**DEF-10 — record keys that name items their own file does not describe.** Eleven `RECORD KEY` declarations exist across the eight programs, and read against the DDS key of the file being opened ten of them look like a match. Read against what the language requires — that the item named belong to the record description of *that file's own* `FD` — four fail, and [the current data model](04-data-model-current-state.md) owns the ownership test applied declaration by declaration.

- **The two on the claims file name an item declared in the policy master's contract.** Both name the claim identifier [QCBLLESRC/CLMMNT.cbl:L47], [QCBLLESRC/CLMADJB.cbl:L52], which the shared contract declares [QCPYSRC/POLDATA.cpy:L139]; their own claims-file record description contains no field of that name. The declaration reads as correct precisely because the name and type match the file's DDS key [QDDSSRC/CLMPF.pf:L67], which is what makes it easy to miss.
- **The two on the servicing file fail twice over.** Both name the whole servicing section of the shared contract [QCBLLESRC/SVCMNT.cbl:L48], [QCBLLESRC/SVCBILB.cbl:L58] — a group whose first subordinate is a two-character amendment-type code [QCPYSRC/POLDATA.cpy:L117], [QCPYSRC/POLDATA.cpy:L118] — and that group belongs to the policy master's contract rather than to the servicing file's own record description. The file itself is keyed on a single service-request identifier [QDDSSRC/SVCPF.pf:L54]. So one side names a composite area beginning with a type code and the other names one column.
- **Every record area in the estate also disagrees in length with the record it reads and writes.** The shared contract is 979 bytes against a 233-byte policy-master record in all seven consumers, and the two secondary files are described at 200, 224 and 324 bytes against records of 127 and 202. The measurements and the offset map are owned by [the current data model](04-data-model-current-state.md).

Two consequences shape the disposition. The first is that this is a **buildability** finding and not merely a schema disagreement: a schema disagreement is something a mapping can arbitrate, whereas a key naming an item outside its file's record description is a construct a compiler is required to reject — which is why [the system inventory](01-system-inventory.md) qualifies its object count and [the operational model](06-operational-model.md) qualifies its build sequence rather than presenting thirteen programs as a set known to exist. The second is that the estate offers nothing that would settle the intended key by itself: the shared contract contains no item corresponding to the servicing file's key at all, so there was no single item available to name, and no physical file declares uniqueness.

Disposition **migrate**: the files and the identity of a service request and a claim are real and are carried across, with one key stated explicitly per table, because today the two halves of each declaration disagree about what identifies a record. The absent uniqueness and referential integrity are owned by [the current data model](04-data-model-current-state.md); the target keys are decided in [the target data model and schema mapping](../target-state/03-target-data-model-and-schema-mapping.md).

**DEF-11 — a duplicated paragraph-number prefix.** The batch claims program carries two paragraphs whose labels both begin `9000-`: an error return [QCBLLESRC/CLMADJB.cbl:L303] and a pending return [QCBLLESRC/CLMADJB.cbl:L311]. The labels are distinct, so this compiles and runs. What breaks is the convention that lets every other program's operation be addressed by its number alone, and [the current-state architecture](02-architecture-current-state.md), which owns the paragraph inventory, records why that matters: rules and tests are anchored by paragraph number, so a duplicated prefix makes one program's anchors ambiguous exactly where behaviour is being captured. Disposition **migrate** — both paragraphs implement wanted behaviour and both are carried across as distinctly named operations.

**DEF-17 — two statement forms that would not compile.** Both sit in the servicing programs, and both were found while inventorying paragraphs rather than while looking for them.

- **An assignment to an item the program never declares, through a qualifier used nowhere else.** One statement qualifies a working-storage item with `OF PROCEDURE DIVISION` [QCBLLESRC/SVCBILB.cbl:L372], at the head of the rider-removal paragraph. Two things are wrong rather than one: a search of the COBOL members and the shared contract finds that qualifier form nowhere else in the estate, and the item itself is declared only in a different member [QCBLLESRC/CLMADJB.cbl:L74] — where it is set [QCBLLESRC/CLMADJB.cbl:L267] and never afterwards read. In the servicing program it is neither declared nor read; the statement is its only occurrence.
- **Four statements leaving an inline loop with a form the language does not define.** `STOP PERFORM` appears at [QCBLLESRC/SVCBILB.cbl:L359], [QCBLLESRC/SVCBILB.cbl:L381], [QCBLLESRC/SVCMNT.cbl:L290] and [QCBLLESRC/SVCMNT.cbl:L307], all four in rider paragraphs. `STOP` takes a run or a literal operand; the construct for leaving an inline `PERFORM` early is `EXIT PERFORM`.

Disposition **migrate**: the rider addition and removal these statements sit inside are wanted behaviour and are carried across, with ordinary loop exits in place of the four undefined ones. The assignment is a different matter, and this document does not assert that it performs wanted behaviour: what it was intended to achieve cannot be recovered from the source, because the name carries an accidental-death meaning in the program that does declare it [QCBLLESRC/CLMADJB.cbl:L74] while the servicing member neither declares nor reads it, so nothing establishes what a rider-removal path was meant to record. The flag is therefore **dropped** as part of the same work rather than carried, both non-standard forms are discarded, and what the path should set — if anything — is an explicit decision the target has to take because the source cannot make it. This is a row rather than a footnote for two reasons: an unexplained idiom is exactly the kind of thing a conversion, automated or manual, mistranslates or silently drops, and both forms belong with the buildability qualifications that [the system inventory](01-system-inventory.md) and [the operational model](06-operational-model.md) now carry.

## Defects in what the system says about itself

Three entries are not defects in behaviour but in description. They are in the register because a migration team reads descriptions to decide what to do, so an inaccurate description causes incorrect work as surely as an inaccurate program produces incorrect output.

**DEF-12 — a superseded company name on a live screen and two report layouts.** The constant `LINCOLN LIFE INSURANCE CO.` appears in three DDS members: the menu screen [QDDSSRC/MNUDSPF.dspf:L22] and the page heading of each printer file [QDDSSRC/POLRPT.prtf:L16], [QDDSSRC/CLMRPT.prtf:L16]. Every source banner in the estate names a different owner, including the banners of those same three members [QDDSSRC/MNUDSPF.dspf:L4], [QDDSSRC/POLRPT.prtf:L4], [QDDSSRC/CLMRPT.prtf:L4], and so does the repository's own overview [README.md:L3]. The screens and reports therefore display one company while the headers of the very files defining them declare another.

The menu instance is the consequential one, and it is not inert: the menu screen's main record format is written on every iteration of the menu loop [QCBLLESRC/MAINMENU.cbl:L60], [QCBLLESRC/MAINMENU.cbl:L63], and the constant sits in that format [QDDSSRC/MNUDSPF.dspf:L19], [QDDSSRC/MNUDSPF.dspf:L22], so this name is on the first screen of every session. Disposition **migrate**, one disposition covering all three sites: the corrected name is carried to the target, and the two report sites are included because DEF-04 makes those headings live output again rather than dormant text.

**This row is documented and not corrected.** Correcting three literals in three DDS members would take one edit each and is exactly what the scope boundary of this assessment forbids: no member of `QCBLLESRC/`, `QCLSRC/`, `QCPYSRC/` or `QDDSSRC/` is modified by this documentation set, and this row is named in that boundary as a specific temptation not to act on. The reason is not procedural. These are display and print constants whose field positions are computed by hand in a fixed-format layout, the estate has no test that would catch a mistake, and the correction has no value until the screens and reports are rebuilt in the target anyway. Recording it costs nothing and loses nothing; changing it spends a source edit on an estate that cannot verify one.

**DEF-13 — two inaccurate descriptions of the estate.** Both are documentation-accuracy defects and both are recorded because they would mislead a reader doing real work.

- A superseded source extension. The batch program's rule paragraphs are annotated in the online program as being the same logic as a member named with a `.CBLE` extension [QCBLLESRC/NBUWMNT.cbl:L220], while the working tree uses `.cbl`. That comment is now the **only** place in the repository where the superseded extension is used as a path: a search of all 24 members returns this one comment, and no path in `docs/` or in the repository overview carries it. The extension does appear elsewhere in `docs/` — including in this sentence — but only as quoted defect text describing the problem, never as a reference intended to resolve. The entry-point document did carry it, in the eight entries of its repository-structure diagram, and it **has already been corrected** as part of this deliverable — those entries now name the actual filenames [README.md:L42-L49]. That correction is why every citation in this documentation set can name a `.cbl` path and have it resolve, and it is the single update in a set that is otherwise entirely additive. The in-source instance cannot be corrected on the same terms as DEF-12, so it is recorded instead.
- A consumer list that omits a consumer. The shared contract's banner names the programs that use it, listing six [QCPYSRC/POLDATA.cpy:L12]. Seven programs copy it; the list omits the inquiry program, which copies it [QCBLLESRC/POLMSTINQ.cbl:L50]. [The current data model](04-data-model-current-state.md) owns this observation and states the consequence precisely: anyone using that banner as the impact list for a contract change would miss a consumer, and the missed one is the only read-only program in the estate — the one whose omission is least likely to surface as a compile failure during ordinary work.

Disposition **migrate** for the row: descriptions of the estate are carried forward corrected, one of the three instances is already actioned at the document level, and the two in-source instances are recorded because the member-level boundary holds.

**DEF-14 — dates are numbers, and the intervals every time-based rule tests are integer differences.** This row has a larger half and a smaller one. The larger half is that no date in this estate is a date. Every date column is declared as zoned decimal with a `YYYYMMDD` comment beside it [QDDSSRC/POLMST.pf:L66-L75], no file declares a date, time or timestamp field, and no program contains an intrinsic date function, a date-format clause or any date-arithmetic construct — the only date-aware verb anywhere retrieves the current date and computes nothing. [The current-state architecture](02-architecture-current-state.md) owns that absence census.

The consequence is that every interval the system tests is an integer subtraction of one eight-digit value from another, received into a plain numeric field: the grace and lapse evaluation is the reference form [QCBLLESRC/SVCBILB.cbl:L198-L199] with its receiving fields at [QCBLLESRC/SVCBILB.cbl:L77-L78], and the same construction drives the reinstatement window [QCBLLESRC/SVCBILB.cbl:L402-L404], the attained-age calculation [QCBLLESRC/SVCBILB.cbl:L189-L191] and both claims windows [QCBLLESRC/CLMMNT.cbl:L230-L233], [QCBLLESRC/CLMADJB.cbl:L235-L238]. A difference computed that way is not a count of days, and nothing in the estate converts it into one; what each guard therefore admits at its boundary is owned by [the current data model](04-data-model-current-state.md). The distinction that matters for a disposition is between the calendar rule each guard was evidently written to express and the arithmetic it actually performs — and both have to be carried into the target deliberately, because a conversion that silently reimplements a guard with real dates changes behaviour rather than preserving it, while one that reproduces the integer arithmetic faithfully preserves a defect. Neither is the default: the target states the calendar rule, and the characterization baseline records the current arithmetic so the change is visible when it is made.

The smaller half is a single inconsistent declaration. The repository states a uniform rule: all date fields use eight-digit `YYYYMMDD` [README.md:L258]. One declaration differs. The menu program declares a six-digit date item — the **declaration** is at [QCBLLESRC/MAINMENU.cbl:L47] and the comment describing it is seven lines later at [QCBLLESRC/MAINMENU.cbl:L54], two separate places, which is worth stating because citing one for the other would misdirect a reader to the wrong line. That comment records the item as a display-only date in `MMDDYY` form. It is populated from the system date [QCBLLESRC/MAINMENU.cbl:L55], moved straight to a screen field [QCBLLESRC/MAINMENU.cbl:L56], and that screen field is itself six digits with an edit code [QDDSSRC/MNUDSPF.dspf:L25].

Both positions are recorded and this register does not resolve the disagreement in prose, in agreement with [the current data model](04-data-model-current-state.md), which owns the date inventory and reaches the same reading: the six-digit item belongs to the one program that copies no contract and opens no database file, it is never moved into any contract item and it is never persisted, so the repository's rule holds for every stored date without exception and the exception is a screen field carrying a two-digit year in a system whose stored dates all carry four.

Disposition **migrate** for the row, covering both halves. Grace, lapse, reinstatement, attained age, both claims windows and the displayed date are all wanted behaviour and are carried across — as real dates, with each boundary restated as the calendar rule it was written to express, and with one representation instead of two. The row is **migrate** rather than **implement** because every one of these decisions is made today and made on the wrong quantity, which is the definition this register uses. How the eight-digit integers become real dates, and what happens to arithmetic that currently spans a month or year boundary, is decided once in [MOD-ADR-006 on date and decimal representation](../decisions/MOD-ADR-006-date-and-decimal-representation.md); the requirement that the characterization baseline record the current integer behaviour rather than a corrected version of it is specified by [the business rule inventory](05-business-rule-inventory.md).

## Records that nothing writes, and attribution that reaches nothing

Two entries concern what stored data actually receives, and both turn on the same thing: an estate whose programs write whole record areas rather than columns cannot be trusted to have populated the columns those areas are meant to fill. One of the two is about a requesting user and one is about a last actor, so both are also attribution defects — which is why the register's boundary matters most here. The facts are recorded and dispositioned below, while their severity belongs to [the security risk register](../risk/01-security-risk-register.md) and the control that closes them to [the security control design](../target-state/04-security-control-design.md).

**DEF-15 — neither secondary file is populated, on any path.** The narrower version of this finding is a single column: the servicing file defines a ten-character requesting-user column [QDDSSRC/SVCPF.pf:L51] that nothing populates. The full version is both files in their entirety, and [the current data model](04-data-model-current-state.md) establishes it with a census rather than an inference.

- **The servicing writer writes an unpopulated area larger than the record.** The only program that writes the file describes its record as a single undifferentiated two-hundred-byte area [QCBLLESRC/SVCMNT.cbl:L58] and writes that area whole [QCBLLESRC/SVCMNT.cbl:L191]; the name of that area occurs exactly twice in the entire estate, the declaration and the write, so no statement anywhere moves a value into it beforehand. The file's own record is 127 bytes [QDDSSRC/SVCPF.pf:L14-L51].
- **The claims writer does the same.** The interactive claims program describes a flat three-hundred-and-twenty-four-byte area [QCBLLESRC/CLMMNT.cbl:L57] and writes it whole [QCBLLESRC/CLMMNT.cbl:L179], against a record of 202 bytes [QDDSSRC/CLMPF.pf:L14-L64].
- **The two batch programs never write their secondary file at all.** The batch servicing program opens the servicing file and closes it with no operation against it in between [QCBLLESRC/SVCBILB.cbl:L92], [QCBLLESRC/SVCBILB.cbl:L124], and the batch claims program does the same with the claims file [QCBLLESRC/CLMADJB.cbl:L84], [QCBLLESRC/CLMADJB.cbl:L121]. Their declarations are the only program-side description of those records' fields, and they are held by the two programs that make no use of them.

So the finding is not that one column has no writer: **no column of either secondary file has a writer**, and each of the two write paths that exists sends an unpopulated area of the wrong length. A servicing-request history and a claim record are declared by the schema and delivered by nothing.

Disposition **implement**. There is nothing to migrate: no column of either file has ever held a value, so a data migration has nothing to carry and both records are new work in the target — with real columns, the requesting user among them. The related fact that a signed-on profile *is* available in the estate — captured by the menu program and immediately displayed, then neither persisted nor passed onward [QCBLLESRC/MAINMENU.cbl:L57-L58] — is what makes the user column an omission rather than an impossibility. The target columns and types for both files are decided in [the target data model and schema mapping](../target-state/03-target-data-model-and-schema-mapping.md).

**DEF-16 — no audit stamp reaches the audit column, and the column receives name text instead.** Two facts have to be read together, and taken separately either one understates the finding.

The first is what the programs do. Five of the six mutating programs stamp the contract's audit user item, and each stamps it with its own program name rather than a user identity — [QCBLLESRC/NBUWB.cbl:L138], [QCBLLESRC/NBUWMNT.cbl:L497], [QCBLLESRC/SVCBILB.cbl:L140], [QCBLLESRC/CLMADJB.cbl:L136] and [QCBLLESRC/CLMMNT.cbl:L281]. The sixth, the interactive servicing program, sets no audit value at all: it applies an amendment by rewriting the policy master and writing a servicing record in two consecutive statements [QCBLLESRC/SVCMNT.cbl:L190-L191], and a search of the member for the contract's audit items returns **zero** occurrences.

The second is where those writes land, and it is the fact that changes the row. The audit items sit at the very end of the shared contract's 979-byte record area — the user item at [QCPYSRC/POLDATA.cpy:L173] — while the policy master's own record is 233 bytes, so the audit pair begins 729 bytes past the end of it. [The current data model](04-data-model-current-state.md) owns the offsets and states the consequence: the part of the record area those five programs stamp is not transferred by any rewrite of this file, however exactly the item and the column correspond by name and type. Meanwhile the ten bytes that *do* land on the audit column [QDDSSRC/POLMST.pf:L78] are the ten bytes at that position in the record area, which are the leading characters of the contract's insured-name item.

So the audit trail is not weak and it is not merely stale on one path: **on every path, the column that is meant to record who last acted receives name text, and the program name each stamping program writes reaches storage on none of them.** The original reading of this row — that one program's omission leaves the previous writer's stamp in place — was the visible half of a defect whose other half is positional, and stating only the first half would have sent a migration looking for a program name in a column that has never held one.

A third instance of the same failure sits in the CL layer and is folded in here rather than given a row, because it is the same defect in a different member. The session-entry program retrieves the job's current library [QCLSRC/STRTLIFE.clle:L24] and concatenates it into a message reading `LIFE400 SESSION STARTED BY` [QCLSRC/STRTLIFE.clle:L31] — the text promises a user and carries a library name. [The operational model](06-operational-model.md) owns that observation and the broader finding it belongs to: no user identity is captured anywhere in the CL layer, so no submitter and no scheduled job records who requested the work.

Disposition **implement** — user-attributed audit records, because nothing in the estate captures a user identity into stored data and there is therefore nothing to carry across. One architectural fact is noted and deliberately not pursued: the two writes at [QCBLLESRC/SVCMNT.cbl:L190-L191] are not atomic, and a search of all COBOL and CL members finds no commitment or rollback operation anywhere. That is recorded here only to explain why the audit gap and the atomicity gap are visible at the same two lines; its severity belongs to [the security risk register](../risk/01-security-risk-register.md) and its recovery consequences to [the continuity and recovery risk document](../risk/03-continuity-and-recovery-risk.md).
