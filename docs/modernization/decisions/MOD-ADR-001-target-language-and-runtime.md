# MOD-ADR-001 — Target language and runtime

This record commits the language and runtime the LIFE400 core is to be rewritten in. It is the first record in the modernization decision log and the most load-bearing one, because every other record and every target-state document assumes an answer to it. It records a decision rather than re-deriving it: the weighted criteria, the hard filter, the candidate scores and the attributed labour-market evidence are owned by [the target-language decision matrix](../talent/02-target-language-decision-matrix.md) and are not restated here. The gap that analysis argues from — what the estate demands of the engineer who maintains it today — is owned by [the skills inventory and gap analysis](../talent/01-skills-inventory-and-gap.md).

**Scope.** This record decides the core language, the runtime line it is taken from, and the server-side application framework. It decides nothing else. The target datastore is to be decided separately in [MOD-ADR-003](MOD-ADR-003-target-datastore.md); how each legacy column is typed is to be decided in [MOD-ADR-006](MOD-ADR-006-date-and-decimal-representation.md); where the target runs, and the exit from the current hardware, are to be deliberately deferred in [MOD-ADR-007](MOD-ADR-007-hardware-exit-deferred.md). All three are planned records: none has been written, so none is accepted and none constrains anything yet. No user-interface component library and no design system is named here or anywhere in this assessment — that selection is an open gap recorded by [the UI modernization document](../target-state/05-ui-modernization.md). No supplier is selected and no tool is procured: conversion-tooling maturity is weighed below as a property of an ecosystem, never as a recommendation to buy anything.

**Reading this record.** A citation of the form `[<path>:<locator>]` is plain text rather than a hyperlink and points at a path in this repository, so it stays meaningful in a diff. Every range cited below was opened and read, and no source member was altered to produce this record. Platform terms link to [the IBM i glossary](../reference/glossary-ibm-i.md) on first use here. No date, duration, ordering or calendar of work appears anywhere below. **The language, the support line it is taken from and the framework are what this record fixes; no release number, framework minor or datastore major is pinned by it**, and [what this record fixes, and what it leaves open](#what-this-record-fixes-and-what-it-leaves-open) states the boundary explicitly. That is a deliberate granularity rather than an omission: what the analysis behind this decision weighs is a property of a language and its ecosystem — an exact decimal type, a labour pool, a tooling ecosystem — and not a property of any one feature release, so fixing a release here would record a choice the evidence does not make. Reproducibility is preserved by fixing the **rule** a release has to satisfy instead of a number, and that rule is testable against the publisher's own statement at the moment a reader reads it.

## Status

**Proposed.**

Nothing in this repository records business acceptance of this decision, so claiming `Accepted` would assert a fact that cannot be cited. The status becomes `Accepted` when the business accepts it. An accepted record is thereafter immutable — it is superseded by a new record that links back to it, never edited — which is the convention for the whole log and will be set out in [the decision log index](README.md), planned and not yet written.

## Context

The business asked to modernize onto "a modern language" without naming one, and that omission is not an oversight to be worked around: naming one is precisely what the second driver asks for. Until a language is named, [Driver 2](../01-business-drivers-and-success-criteria.md) has no answer at all, and `SC-2.1` — exactly one language and runtime named for the core, recorded in a record carrying a status, with no other document naming a different one — cannot be met by any amount of further analysis.

The estate the target replaces is written in three platform-locked languages and declares as much in its own overview [README.md:L4], against a declared runtime baseline of `ILE COBOL V3R7 · OS/400 V4R2 · IBM AS/400 Model 9406` [README.md:L264]. What that baseline means for fix supply is established, with attribution, by [the platform and support status document](../current-state/03-platform-and-support-status.md); the only bearing it has here is that a target whose own runtime carried no published support line would reproduce the exposure this programme exists to remove.

The constraint that actually decides the choice comes from the code rather than from the labour market. Money in this system is a fifteen-digit quantity with two decimal places, and that precision is declared **twice, independently, in two languages that agree**. On the stored side, [DDS](../reference/glossary-ibm-i.md#dds-data-description-specifications) declares the monetary columns of the policy master as [zoned decimal](../reference/glossary-ibm-i.md#zoned-decimal) at `15S 2` — the sum assured [QDDSSRC/POLMST.pf:L52], the loan balance [QDDSSRC/POLMST.pf:L54], the annual premium [QDDSSRC/POLMST.pf:L59], the modal premium [QDDSSRC/POLMST.pf:L61] and the outstanding premium [QDDSSRC/POLMST.pf:L63] — and declares the same precision again in the other two keyed [physical files](../reference/glossary-ibm-i.md#physical-file), for the servicing premium delta [QDDSSRC/SVCPF.pf:L45] and the claim settlement amount [QDDSSRC/CLMPF.pf:L52]. On the program side, the shared [copybook](../reference/glossary-ibm-i.md#copybook) declares the same quantities as thirteen integer digits plus two decimals, seven of them in the premium-results group alone [QCPYSRC/POLDATA.cpy:L98-L105]:

```text
QDDSSRC/POLMST.pf    SUMASSR  15S 2        zoned decimal, 15 digits, 2 decimals
QCPYSRC/POLDATA.cpy           PIC 9(13)V99  13 integer digits + 2 decimals - the same precision
```

Two independent declarations of one precision is the signature of a business invariant rather than of one file's type system, so the requirement survives the migration intact. Three further facts sharpen it from a storage question into an arithmetic one:

- **Exactly one item in the whole shared contract can hold a negative value** — `PM-PREMIUM-DELTA` [QCPYSRC/POLDATA.cpy:L106], the amendment repricing delta, computed on the batch servicing path as the new total annual premium minus the old [QCBLLESRC/SVCBILB.cbl:L428-L429] and persisted as a `15S 2` column [QDDSSRC/SVCPF.pf:L45]. It is the figure an operator reads back to a policyholder whose premium has just changed, so a representation error there surfaces as a disputed charge rather than as a rounding artifact in a log.
- **The premium expressions produce more decimal places than the fields receiving them.** The modal premium divides the total annual premium by a billing divisor of one, two, four or twelve and then multiplies by a four-decimal loading factor [QCBLLESRC/NBUWB.cbl:L462-L464]; the tax amount multiplies a fifteen-digit, two-decimal value by a four-decimal rate [QCBLLESRC/NBUWB.cbl:L443-L444]. Division by twelve does not terminate in decimal. Scale is not uniform either — a four-decimal flat extra rate sits alongside two-decimal money in the same record [QDDSSRC/POLMST.pf:L49] — so a single fixed money type is insufficient and a configurable-scale decimal type is required. The field-level enumeration behind that is owned by [the current data model](../current-state/04-data-model-current-state.md).
- **Every one of those results is truncated silently.** The exhaustive search establishing that no `COMPUTE` in the estate carries a `ROUNDED` phrase and no arithmetic statement carries an `ON SIZE ERROR` clause belongs to [the decision matrix](../talent/02-target-language-decision-matrix.md), which also owns the count of `COMPUTE` statements across the eight [ILE](../reference/glossary-ibm-i.md#ile-integrated-language-environment) COBOL programs. Reproducing this system's outputs therefore means reproducing truncation at a declared scale, not applying whatever rounding a default supplies — and the tolerance policy that comparison is judged against will be set by [the parallel-run and output-parity document](../migration/06-parallel-run-and-output-parity.md), which is planned and not yet written.

One final property of the estate raises the stakes on everything above: it contains no test member of any kind, so a conversion arrives with no behavioural net beneath it. That absence is established by the census in [the current-state architecture](../current-state/02-architecture-current-state.md#what-is-absent), and it is what will make the planned [MOD-ADR-008](MOD-ADR-008-characterization-tests-first.md) — together with the planned [characterization test strategy](../migration/05-characterization-test-strategy.md) — a precondition rather than a nicety.

## Decision Drivers

Each driver below is traced to one of the two stated business drivers or to a resolution in the ambiguity register. Driver 2 and `A-01` dominate this decision; Driver 1 bears on it only indirectly, through the platform baseline and through the fact that a monetary representation error is a risk as much as a defect.

- **Exact decimal arithmetic at the legacy precision is a correctness gate, not a weighted preference** — Driver 2 via `SC-2.4`, and Driver 1 indirectly. It is applied as a pass/fail filter *before* anything is weighed, because a candidate must not be able to accumulate points elsewhere and score its way past a correctness requirement [QDDSSRC/POLMST.pf:L52], [QCPYSRC/POLDATA.cpy:L106].
- **Depth of the enterprise labour pool for regulated back-office work** — Driver 2, and the driver restated as a measurable property. This is deliberately narrower than language popularity: what the business needs is people who can be hired to maintain a transactional policy-administration core, which is a different question from which language the most developers use. `SC-2.2` requires that claim to rest on attributed third-party evidence, which [the decision matrix](../talent/02-target-language-decision-matrix.md) supplies and this record does not restate.
- **Maturity of COBOL-conversion tooling for the target** — Driver 2 and Driver 1 together. It serves Driver 2 because tooling emitting idiomatic target-language output is what makes the result maintainable by new hires, and Driver 1 because every hand-converted line is a line where a rule can be lost with no test to catch it. The rule corpus at stake, and how much of it carries a stable source anchor, is quantified by [the business rule inventory](../current-state/05-business-rule-inventory.md).
- **A published support line for the runtime itself** — Driver 1. Choosing a target with no support line would reproduce the exposure the declared baseline already creates [README.md:L264] in a new language, which is the one outcome worse than doing nothing.
- **Freedom from the four platform competencies the estate demands together** — Driver 2 via `SC-2.3` and `SC-2.9`. Any mainstream candidate satisfies this, so it discriminates weakly between the options and strongly against the status quo.
- **One primary recommendation with a documented runner-up, recorded supersedably** — `A-01`. The register pre-registers this outcome, and this record is where it is carried, so a later reversal supersedes one record rather than editing analysis prose in a dozen places.

## Options Considered

Five candidates were evaluated. The filter column is the exact-decimal gate applied before any weighting; the weighted total and rank are the scores computed by [the decision matrix](../talent/02-target-language-decision-matrix.md), reproduced here so the outcome is auditable from this record and attributed there rather than presented as new analysis.

| Candidate | Filter verdict | Weighted total / rank | Why it was or was not chosen |
|---|---|---|---|
| Java, on a current long-term-support release, with Spring Boot | Passes without conditions | 447 / 1 | **Chosen.** Its standard-library decimal type is the conventional money representation, carries its scale as part of the value, and refuses an inexact division unless given a rounding mode — which forces the truncation this estate performs silently [QCBLLESRC/NBUWB.cbl:L462-L464] to be written down deliberately. Using it is still a deliberate act rather than a default, which the consequences below carry as an obligation. Broadest published conversion coverage of the five across the components the matrix scores, and the deepest adoption evidence for regulated back-office work — adoption evidence, not a hiring measurement, which is why it does not score full marks on either criterion. First-class restartable batch support, a published support line, and multiple independent runtime builds so patch supply does not rest on one supplier |
| C#/.NET | Passes without conditions | 411 / 2 | **Runner-up, not a foil.** Its decimal type is built into the language with its own literal form, making an accidentally binary monetary value a visible mistake in source — arguably a better ergonomic than the chosen candidate. Level on typing, support cadence, security tooling, relational decimal mapping and now on labour-pool depth, where the two candidates tie because neither has a hiring measurement behind it. It ranks second on the exact-decimal ergonomics of division and on published conversion breadth, not on any deficiency: tooling for this target names ILE COBOL but not the CL layer or an IBM i database path |
| Python | Passes only under a standing discipline | 307 / 3 | **Evaluated and rejected for the core.** Its standard-library decimal type and explicit rounding context are excellent, but the language's own numeric default is binary floating point, so exactness becomes a convention every engineer must hold at every arithmetic site. Decisively, its type-checking safety net is opt-in rather than inherent — annotations, static checkers and refactoring tools all exist, but their coverage is a property of the codebase rather than of the language — which matters most in a conversion with no existing tests; conversion tooling depth is also thin. Retains a legitimate role in migration validation, reconciliation and checksum comparison |
| TypeScript/Node | Does not pass | 275 / 4 | **Evaluated and rejected for the core.** The sole built-in numeric type is binary floating point and exact decimal is a third-party dependency, so correctness for the monetary fields [QDDSSRC/POLMST.pf:L52] would rest on convention at every arithmetic site and every driver boundary; the arbitrary-precision integer type cannot carry a scale and does not substitute. Weaker on restartable batch work: long-running work is routinely moved off the event loop, but chunk-oriented restart, skip and retry semantics would be assembled rather than adopted. Not rejected for a presentation tier performing no monetary arithmetic — a separate decision, deferred elsewhere |
| Go | Does not pass | 265 / 5 | **Evaluated and not selected.** Neither the language nor its standard library has a decimal type, and the standard database interface has none to map a fixed-scale column into, so each such column carries a per-column obligation — pervasive here, and worse because the scales are not uniform [QDDSSRC/POLMST.pf:L49]. Weakest of the five on both decisive labour criteria. Well suited to operational and infrastructure services around the core |

None of the three set aside is rejected as a bad language, and none is rejected on a general preference. Each is set aside against criteria derived from this estate, and each rejection names the specific property that disqualifies it for a policy-administration core.

## Decision

**The LIFE400 core is to be rewritten in Java, on a current long-term-support release, with Spring Boot as the server-side application framework.** C#/.NET is recorded as the documented runner-up: if this decision is revisited, that is the candidate it should be revisited in favour of.

Three rules attach to that table, and they are what make it a decision rather than a gesture.

- **The decision is the language, the support line and the framework — and a change to any of those three is a superseding record.** Selecting a concrete release under the rule above is not such a change and needs no new record; changing the language, abandoning the long-term-support constraint, or changing the framework each is. That is the same discipline this log applies to every other reversible choice, applied at the granularity the evidence actually reaches.
- **Every rule above is a condition, not a date.** Each is testable against the publisher's own statement at the moment a reader reads it: a release carries the designation or it does not; it is inside its stated window or it is not; the framework supports it or it does not. No calendar appears here, and none is needed.
- **The runner-up is a candidate, not a second stack.** C#/.NET is recorded as the documented alternative and carries no release or framework selection of its own: making one for a runtime that is not being built on would be a decision nobody has taken. If the runner-up is ever selected, the record that selects it states its own components under the same three rules.

**What consumes this table.** Every document that needs the target stack states this position and links here rather than re-deriving it — the executive layer through [the business drivers and success criteria](../01-business-drivers-and-success-criteria.md), the analysis through [the target-language decision matrix](../talent/02-target-language-decision-matrix.md), the destination through the target-state layer beginning at [the target architecture](../target-state/01-target-architecture.md), and the route through [the strategy options and selection document](../migration/01-strategy-options-and-selection.md). That is what makes a superseding record a single-file change: the decision lives here, and nine documents point at it.

## Consequences

The honest costs are named alongside the benefits. A record listing only benefits would not be a decision record.

- **Positive — the driver is answered rather than deferred.** Exactly one language and runtime is now named for the core, discharging `SC-2.1`, and every other document that needs the answer links here instead of restating it. Hiring can be specified against a named stack.
- **Positive — the stack supplies mature exact-decimal facilities and a place to enforce them, and discipline is still required.** The standard library provides a decimal type that carries its own scale and refuses an inexact division without an explicit rounding mode, so the truncation this estate performs silently becomes something written down and reviewable, which is what makes field-level output parity achievable at all. It does not become automatic: the language's own literals and arithmetic operators are primitives, so the decimal type must be named at every monetary declaration, and constructing one from a binary literal rather than from a string reintroduces the error the type exists to prevent. **Three obligations therefore sit with this programme rather than with the language** — a written standard fixing the monetary type and the rounding mode at each operation, static enforcement of that standard in the build so a primitive on a money path fails rather than merely displeases a reviewer, and characterization assertions that check the type as well as the value. What the choice buys is that all three are straightforward to enforce here and would be harder or impossible in three of the five candidates evaluated.
- **Positive — the conversion runs with the grain of what tooling exists, within a stated bound.** The ecosystem with the broadest published conversion coverage for this platform family, and with the deepest adoption in regulated back-office work, is the same ecosystem, which reduces the volume of unguarded hand conversion in an estate with no tests. The bound matters and is recorded rather than implied: published offerings address the procedural logic, the database definition and — in one case — the CL layer, address the 5250 presentation contract only as a like-for-like rendering, and address the operational reconstruction and the missing characterization suite not at all. Tooling reduces the hand conversion; it does not remove the need for the behavioural net, which is why the planned [MOD-ADR-008](MOD-ADR-008-characterization-tests-first.md) is a precondition rather than a parallel activity.
- **Negative — JVM operational skills must be hired or built, and they are not the same skills as writing Java.** Runtime tuning, garbage-collection behaviour, heap sizing and diagnostics under load are a distinct competency. Trading IBM i work-management expertise for JVM operational expertise narrows the pool problem but does not eliminate an operational-knowledge dependency; it relocates it.
- **Negative — Spring Boot is an opinionated framework and its conventions have to be learned.** Configuration, dependency injection, transaction boundaries and its batch abstractions each impose a way of working. Engineers hired for language fluency are not thereby fluent in the framework, and the framework's own major-version upgrades become a recurring obligation.
- **Negative — deciding at the level of a support line leaves a real decision to be taken downstream, and it has to be taken deliberately.** Someone still has to select a release and a framework line, and record the selection, under the rule this record states. That obligation is named here rather than hidden, because the estate this programme exists to replace runs a platform release far outside its own support window [README.md:L264] and got there by nobody having written down which release was in use or having tracked what happened to it. Deciding the rule rather than the number is what keeps this record true across readings; it is not a licence to leave the number unchosen or unrecorded once an implementation exists, and it is not a substitute for tracking the window the selected release sits in.
- **Negative — exact-decimal arithmetic in Java is verbose next to COBOL's native fixed-point declarations.** In the legacy estate, precision is declared once in a picture clause [QCPYSRC/POLDATA.cpy:L98-L105] and the arithmetic reads as ordinary expressions [QCBLLESRC/NBUWB.cbl:L443-L444]. In the target it becomes explicit method calls with an explicit scale and rounding mode at each operation. The conversion must be deliberate about this rather than incidental: it is the point at which a mechanical translation most easily reintroduces a binary numeric type, and it is the same obligation named in the first positive consequence above rather than a second, separate one — stated in both places because a reader taking only the benefits would otherwise read the guarantee as stronger than it is.
- **Negative — the leading candidate scores worst of the five on developer desirability.** The matrix scores this openly rather than hiding it. Driver 2 asks for a pool that can be hired from rather than for the language engineers most want to use, so it does not change the outcome; it does mean role attractiveness is a live concern for filling and holding a position, and this record should not be read as making that concern disappear.
- **Negative — choosing one core language forecloses polyglot experimentation in the core.** That is the intended effect and it is still a cost. A single implementation of each domain's rules is the point of the planned [MOD-ADR-004](MOD-ADR-004-single-domain-rules-service.md), and a polyglot core would defeat it. Rejection "for the core" is not rejection everywhere: the languages set aside above remain appropriate in the supporting roles named against each, and nothing here constrains the presentation tier, whose component selection is an untaken decision owned by [the UI modernization document](../target-state/05-ui-modernization.md).
- **Neutral, and easy to over-read — a supported language does not by itself deliver patch supply.** The matrix records attributed evidence that organisations in this very sector run unsupported components in production. The upgrade discipline still has to be maintained; choosing a runtime with a published support line only makes it possible.
- **Consequential for other records, each of which is planned rather than written.** [MOD-ADR-003](MOD-ADR-003-target-datastore.md) will inherit the requirement that the datastore expose a fixed-scale exact numeric column type mapping to the chosen decimal type without loss; [MOD-ADR-006](MOD-ADR-006-date-and-decimal-representation.md) will inherit the representation rule itself; [MOD-ADR-007](MOD-ADR-007-hardware-exit-deferred.md) is to remain deliberately separate, because a language decision and a hardware decision rest on different evidence and have different blast radii.
- **Supersedable, on two distinct kinds of trigger.** This is a decision with a status, not a fact. One kind is evidential, and both criteria most likely to move would move on evidence this assessment could not obtain rather than on argument: a hiring measurement for back-office insurance work by language, which would replace the adoption proxy both leading candidates are scored on and could separate them in either direction, and a published result from an actual ILE COBOL conversion covering the CL, database, presentation and operational components together, which nothing consulted supplies for any candidate. The other kind is lifecycle, and it is the one [what this record fixes, and what it leaves open](#what-this-record-fixes-and-what-it-leaves-open) makes testable — the publisher ceasing to designate long-term-support releases for the language, or the framework ceasing to support the releases so designated, either of which would invalidate the rule rather than merely a selection made under it. Both kinds produce the same response: a new record that links back to this one. Neither produces an edit to this record, because an accepted record in this log is immutable.
