# MOD-ADR-005 — Authentication and authorization

This record commits an explicit identity and role model for the LIFE400 target, in place of the as-built posture of delegating every access-control decision to the platform beneath the application. It records a decision rather than designing the controls that carry it out: the findings it answers are owned and numbered by [the security risk register](../risk/01-security-risk-register.md), and the control-by-control design — `CTL-AUTH`, `CTL-ROLE` and `CTL-AUDIT`, together with the authentication and authorization flow it draws as its own diagram — is owned by [the target security control design](../target-state/04-security-control-design.md). Neither is restated here. The personal and health data whose exposure gives this decision its urgency is inventoried by [the compliance and data protection document](../risk/02-compliance-and-data-protection.md), and the security control gap map belongs to the register rather than to this record.

**Scope.** This record decides three things: that authentication becomes an application-level concern establishing a principal that is verified rather than assumed; that an explicit role model exists; and that authorization is enforced at the service and record boundary rather than at the screen. It decides nothing else. It names no product, supplier, protocol, authentication factor or token format, and it recommends nothing to procure or license — those are implementation choices the control design deliberately leaves open, and naming one here would fix a decision the evidence does not make. It does not enumerate operations, which are owned by [the program-to-service map](../target-state/02-program-to-service-map.md), and it does not type the columns that will hold an attribution, which are owned by [the target data model and schema mapping](../target-state/03-target-data-model-and-schema-mapping.md). The sign-in surface itself is an interface-component decision that no document in this assessment takes: no component library and no design system is named here or anywhere in it, and that open gap is recorded by [the UI modernization document](../target-state/05-ui-modernization.md).

**Reading this record.** A citation of the form `[<path>:<locator>]` is plain text rather than a hyperlink and points at a path in this repository, so it stays meaningful in a diff. Every range cited below was opened and read, and **no source member was altered to produce this record**: this is a plan, not a remediation, and nothing below has been applied to the running system. Platform terms link to [the IBM i glossary](../reference/glossary-ibm-i.md) on first use here. No date, duration or ordering of work appears anywhere. **No regulatory framework is asserted to apply**, in either direction — the gaps below are described generically, and framework applicability is a confirm-with-the-business item under `A-03` in [the business drivers and success criteria](../01-business-drivers-and-success-criteria.md). The only compliance activity this repository evidences at all is the Y2K review [README.md:L258-L259].

## Context

LIFE400 does not have a weak identity model. It has almost none, and its own source says so with unusual candour: **there are four distinct places where the design reaches for an identity and then stops.**

- **Authentication is delegated wholly to the platform sign-on.** The entry program's header documents how it is installed, as a user's [initial program](../reference/glossary-ibm-i.md#initial-program) [QCLSRC/STRTLIFE.clle:L14-L16]. By the time any LIFE400 code runs a profile has already been established by something outside LIFE400, and nothing inside LIFE400 examines it. That is the single occurrence of a user-profile keyword anywhere in the tree, and it configures *what runs* at sign-on rather than *whose authority it runs under* — a distinction the glossary keeps separate from [adopted authority](../reference/glossary-ibm-i.md#adopted-authority) precisely because conflating the two would overstate this system's posture.
- **The signed-on profile is captured and then merely displayed.** The menu program accepts it from the platform and, on the very next line, moves it into a screen field [QCBLLESRC/MAINMENU.cbl:L57-L58]. It is never persisted and never passed onward: the working-storage item holding it is referenced nowhere else in the program.
- **Nothing consults it.** The interactive dispatch is one inline loop [QCBLLESRC/MAINMENU.cbl:L60-L92] whose only branch is a selection test, so **every signed-on user is offered the identical option set**, and the four destinations are compile-time literals [QCBLLESRC/MAINMENU.cbl:L73], [QCBLLESRC/MAINMENU.cbl:L75], [QCBLLESRC/MAINMENU.cbl:L77], [QCBLLESRC/MAINMENU.cbl:L79]. That no identity, role, permission or encryption logic exists anywhere in the estate is not an impression formed from this program alone: it is established as an exhaustive census by [the current-state architecture](../current-state/02-architecture-current-state.md#what-is-absent), and this record relies on that census rather than restating its search.
- **The attribution column exists, is the right width, and holds the wrong subject.** The shared contract declares a ten-character last-action user [QCPYSRC/POLDATA.cpy:L173] persisted as a column of the policy-master [physical file](../reference/glossary-ibm-i.md#physical-file) [QDDSSRC/POLMST.pf:L78], and five programs fill it with a literal naming *themselves* [QCBLLESRC/NBUWMNT.cbl:L497], [QCBLLESRC/NBUWB.cbl:L138], [QCBLLESRC/SVCBILB.cbl:L140], [QCBLLESRC/CLMADJB.cbl:L136], [QCBLLESRC/CLMMNT.cbl:L281].
- **On the estate's dedicated amendment path it holds something worse than the wrong subject: it holds a stale one.** The interactive servicing program rewrites the policy master [QCBLLESRC/SVCMNT.cbl:L190] and writes an amendment record [QCBLLESRC/SVCMNT.cbl:L191] without setting the attribution field anywhere in its 448 lines, so the column retains the *previous* writer's stamp across a mutation it did not perform.
- **A requesting-user column was designed in and then made unfillable.** The servicing file declares one [QDDSSRC/SVCPF.pf:L51], but the writing program describes that record as a single flat area [QCBLLESRC/SVCMNT.cbl:L58] and writes it undifferentiated [QCBLLESRC/SVCMNT.cbl:L191], so no writer can populate it.

Someone intended attribution at each of those points and it was never wired up. Two further properties of the estate bear directly on the decision. Object authority is left entirely undeclared: the application library is created with no authority specification [README.md:L125] and so are the supporting work-management objects [README.md:L199-L206]. And the only interface is a workstation [display file](../reference/glossary-ibm-i.md#display-file) reached over a raw [5250 datastream](../reference/glossary-ibm-i.md#5250-datastream) [QCBLLESRC/MAINMENU.cbl:L32-L36], with no transport-protection construct declared anywhere in the estate. Because the declared platform baseline is far outside the line that still receives fixes [README.md:L264] — established, with its publisher attributed, by [the platform and support status document](../current-state/03-platform-and-support-status.md) — a weakness in the delegated sign-on or in that datastream is not a defect that can be patched where it lives.

These observations are numbered as findings, with severity and impact, by [the security risk register](../risk/01-security-risk-register.md), and this record references those identifiers rather than re-deriving their rows.

## Decision Drivers

Driver 1 dominates this record. Driver 2 bears on it only indirectly, and the connection is worth naming because it is easy to miss: a platform-delegated posture is only auditable by someone fluent in that platform's authority model, so leaving identity implicit keeps the reviewer pool as narrow as the maintainer pool.

- **Four numbered findings are blocked on one unresolved question** — Driver 1, via `SC-1.1`. `SEC-01`, `SEC-02`, `SEC-06` and `SEC-07` in [the register](../risk/01-security-risk-register.md) all depend on what a principal *is* in the target and how it reaches the point of a write. Settling that once, here, is what stops four rows of prose from each carrying their own rationale.
- **Attribution has to name an actor, and the actor is not always a person** — Driver 1, via `SC-1.3`. Two of the four mutating entry paths have no contemporaneous human at all, so a model admitting only human users would be unsatisfiable by construction and would invite a fabricated one. The principal kinds that resolve this are designed by [the target security control design](../target-state/04-security-control-design.md).
- **Access must be differentiated by role, and no role evidence exists to migrate** — Driver 1, via `SC-1.4`. The identical option set for every user [QCBLLESRC/MAINMENU.cbl:L60-L92] means a role model must be *derived*, which makes it a business exercise rather than a translation.
- **Enforcement must sit where every caller passes, and some callers never see a screen at all.** The three submitters take business keys and no identity [QCLSRC/RUNNBUW.clle:L21], [QCLSRC/RUNSVC.clle:L21], [QCLSRC/RUNCLM.clle:L21], and the nightly driver takes no parameter whatsoever [QCLSRC/DLYUPD.clle:L24]. The engines they reach declare no workstation file, so there is no screen on those paths to enforce at even in principle [QCBLLESRC/NBUWB.cbl:L50-L54], and none of these entry points is reachable from the interactive dispatch [QCBLLESRC/MAINMENU.cbl:L60-L92].
- **The gaps are described without asserting a framework** — `A-03`. Naming a regulation as applicable would assert a fact this repository cannot evidence.
- **The decision is recorded, not performed** — `A-08`. This record changes no member, hardens no authority and alters no profile.

## Options Considered

Five options were evaluated. Each rejection names the specific property of *this* estate that disqualifies it, rather than a general preference.

| Option | Verdict | Why, against this estate |
|---|---|---|
| An explicit application-level identity and role model: authentication establishing a verified principal, a defined role set, and authorization enforced at the service and record boundary | **Chosen** | The only option that can express a role where no role construct exists, carry an actor to the point of a write so an attribution names a subject rather than a program, and apply the same decision to a caller that never renders a screen. It closes `SEC-01`, `SEC-02`, `SEC-06` and `SEC-07` at one point instead of four |
| Continue delegating identity to the platform sign-on and add nothing | Rejected | It cannot express a role, because the application never observes the profile it is given [QCBLLESRC/MAINMENU.cbl:L57-L58]; it cannot attribute a record, because the identity never reaches a writer and five writers therefore name themselves; it cannot even refuse or record a failed authentication, because the application never sees one. Decisively, it leaves the control on a release that receives no fixes [README.md:L264], so the one component the posture depends on is the one component that cannot be remediated |
| Delegate authentication to an external identity provider and keep no application-side role model | Rejected | It answers only `SEC-01`. A verified principal with nothing to authorize against still offers every capability to everyone, so `SEC-02` survives intact; and a provider that authenticates a caller but is never consulted at a write leaves `SEC-06` and `SEC-07` open too. This option is not the same as the chosen one with a supplier attached — the chosen model treats a delegated provider as one admissible shape for the identity source while still requiring a role model and an enforcement point of its own |
| Enforce authorization only at the user-interface layer, by rendering a restricted menu | Rejected | The batch paths bypass the interface entirely: three submitters accept business keys and no identity [QCLSRC/RUNNBUW.clle:L21], [QCLSRC/RUNSVC.clle:L21], [QCLSRC/RUNCLM.clle:L21], the nightly driver accepts no parameter [QCLSRC/DLYUPD.clle:L24], and none is reachable from the menu loop [QCBLLESRC/MAINMENU.cbl:L60-L92]. A restricted menu would therefore protect the one entry path that already displays an identity while leaving the mutating paths that never had one wide open. A screen is a usability surface, not an enforcement point |
| Keep platform delegation but harden object authority around it | Rejected as sufficient, retained as necessary | Declaring authority closes a different finding, `SEC-03`, and is required regardless. It cannot substitute here: the platform's protection unit is the object, and an object grant cannot distinguish reading a policy from amending it once a program holds that file open for update — which the servicing program does [QCBLLESRC/SVCMNT.cbl:L79], while only the inquiry program opens it for input alone [QCBLLESRC/POLMSTINQ.cbl:L63]. Nor does it produce an attribution — the column would still name the program [QDDSSRC/POLMST.pf:L78] |

## Decision

**The LIFE400 target adopts an explicit identity and role model: authentication is performed at the application boundary and establishes a principal that is verified rather than assumed; a defined role set exists; and authorization is enforced at the service and record boundary, on every caller, including callers that never render a screen.** The principal is carried through the call path so that every mutation is attributed to the actor that performed it, and to the identity that requested it where those differ.

### What this record supersedes, and what it does not

It supersedes the as-built decision to delegate access control wholly to the platform — **in the target only.** That qualification is the substance of this section rather than a caveat attached to it. Three consequences follow, and all three are load-bearing.

- **Nothing about the running system changes.** No authority is hardened, no profile is altered, no member is edited, and no finding in the register is closed by this record's existence. The eight findings remain open with named target controls; this record chooses the model those controls are designed against, and a reader must not take any sentence here as a remediation that has been applied.
- **The as-built decision remains the accurate record of the legacy system.** It correctly describes what LIFE400 does, and superseding it neither rewrites that history nor makes it retrospectively wrong. Immutability of an accepted record is one of this assessment's stated practices: a record is superseded by a new one that links back, never edited, and the as-built record continues to be the right description of the system it was written about.
- **The supersession is scoped to access control and to nothing else.** It does not disturb any other as-built decision, and it says nothing about whether the platform sign-on continues to exist behind a coexistence boundary while both systems run — a migration question owned by the recommended path.

### The role model is an inference, not an inventory

The role set is derived from the **only** signal of intended capability the estate contains: the option list the menu offers and the programs it offers them through [QDDSSRC/MNUDSPF.dspf:L30-L35]. The derivation itself, capability boundary by capability boundary, is owned by [the target security control design](../target-state/04-security-control-design.md) and is not reproduced here. What this record fixes is its epistemic status, because that is what a later reader is most likely to get wrong: **it is a proposal requiring business confirmation, not a catalogue read out of the source.** No user population, group or authorization list is described anywhere in the repository, so there is nothing to test the boundaries against; and the absence of role branching is evidence that the question was never asked, not evidence that roles are unnecessary. Those two readings look identical in the source and are opposite in consequence. Accordingly, this record requires that a role model exist and be enforced; it does not fix its membership, its cardinality, or whether any capability should be split between a maker and a checker — the estate never encoded an answer to that, and inventing one here would be the derivation hardening into a false finding.

## Consequences

The honest costs are named alongside the benefits. A record listing only benefits would not be a decision record.

- **Positive — one decision unblocks four findings and one criterion each for identity, attribution and role.** `SEC-01`, `SEC-02`, `SEC-06` and `SEC-07` acquire a common answer, and `SC-1.1`, `SC-1.3` and `SC-1.4` become achievable rather than aspirational. A superseding decision changes this one file rather than four passages of prose across the register and the control design.
- **Positive — attribution becomes capable of naming a subject.** A carried principal is what lets an audit record name an actor and its type, which is the difference between the target's audit trail and a column holding the name of the program that wrote it [QDDSSRC/POLMST.pf:L78].
- **Negative — an identity and role model is net-new surface, and it brings its own attack surface and its own operational burden.** The estate has no credential, session or key material to protect because it has none at all — the census in [the current-state architecture](../current-state/02-architecture-current-state.md#what-is-absent) — and the target introduces all three. Credential lifecycle, session issuance, expiry and revocation, secret and key handling and rotation, and the failure modes of an identity component that is unreachable or misconfigured are new obligations, and an authentication component is itself a target. This is a real exchange: a class of exposure the estate does not have is accepted in return for controls it cannot express.
- **Negative — the role model is a hypothesis the business must confirm, and getting it wrong fails in both directions.** It is inferred from a menu that draws no distinctions between its users. Too narrow and users are locked out of work they are expected to do; too broad and the model grants exactly the undifferentiated access it was introduced to remove — with the added hazard that an over-permissive role *looks* like a working control. This is the single largest open item in this record, it cannot be closed by further reading of the source, and it must not be resolved by inference a second time.
- **Negative — user-attributed audit changes what the existing column means, and history cannot be repaired.** Rows written by the legacy system hold a program name [QCBLLESRC/NBUWB.cbl:L138] or, on the servicing path, a stale name belonging to an earlier writer [QCBLLESRC/SVCMNT.cbl:L190]. **No retro-attribution is possible**, because the information required to compute one was never captured. Legacy rows must therefore be distinguishable from attributed ones rather than migrated as though they were equivalent — the schema position that follows from this is owned by [the target data model and schema mapping](../target-state/03-target-data-model-and-schema-mapping.md) — and any report or investigation spanning the boundary must read the two differently. Presenting a program name in a column labelled as a user is a worse outcome than an acknowledged gap, because it is indistinguishable from a true attribution after the fact.
- **Negative — two authorization models exist at once while both systems run, and they must be reconciled per stage.** The legacy path continues to delegate to the platform while the target enforces its own model, so for any capability reachable from both, the effective authority is the union of two mechanisms that share no vocabulary and cannot be reviewed together. Each stage must state which system owns the decision for which capability; a gap in that statement is a privilege gap, and it will not be visible in either system's own configuration.
- **Neutral, and easy to over-read — a role model is not a user directory, and neither is a secret store.** The boundary between where end-user identities live and where the services' own key material lives is a design property this record depends on but does not own; collapsing the two is the most common way a sound control set acquires a component with far more authority than any of its jobs needs. The boundary is specified by [the target security control design](../target-state/04-security-control-design.md).
- **Consequential for other work.** Three controls in the control design are written against this model, the requesting-user column becomes a real attribution rather than an unfillable declaration [QDDSSRC/SVCPF.pf:L51], the navigable surface renders only what a principal holds, and the shared servicing screen splits into an editable and a read-only view — a mapping owned by [the UI modernization document](../target-state/05-ui-modernization.md). The read-side auditability gap and the retention and erasure gaps are owned by [the compliance and data protection document](../risk/02-compliance-and-data-protection.md).
- **Supersedable, on evidence this assessment could not obtain.** A confirmed statement of how the business actually divides this work would replace the derived role model, and could enlarge it, shrink it, or restructure it around a maker-and-checker split. That is a new record linking back to this one, never an edit to this one.
