# Business Drivers and Success Criteria

This document is the requirements baseline for the LIFE400 modernization assessment. It does one thing: it converts the business request that commissioned this work into criteria that can be checked, and it records — once, authoritatively — the resolution of every question that request left open. It is the second document a decision-maker reads, and it is the reference the rest of the set is measured against, because a recommendation can only be judged against a written statement of what was asked for. The request itself is a single sentence. It is reproduced verbatim below and is never paraphrased, tidied or extended anywhere in this set.

**Scope.** This document owns three things and nothing else: the verbatim requirement, the measurable success criteria for each of the two stated business drivers, and the ambiguity register that resolves what the requirement left unsaid. It does **not** recommend a path — that will be [the executive recommendation](00-executive-recommendation.md), which is planned and not yet written. It does **not** analyse the system; the current-state layer does that, beginning at [the system inventory](current-state/01-system-inventory.md). It does not register or rate a finding, which is [the security risk register](risk/01-security-risk-register.md); it does not name a target language, which is [the target-language decision matrix](talent/02-target-language-decision-matrix.md); it designs no control, which is [the target security control design](target-state/04-security-control-design.md); and it sequences no work, which is [the recommended path](migration/02-recommended-path.md).

**Delivered and planned are distinguished throughout, and the distinction is load-bearing.** Some documents this one points to exist and can be opened now; others are planned and their paths are given so the forward dependency is unambiguous once they are written. Where a document is not yet written, the sentence pointing at it says so — "planned", "pending", "will be recorded" — rather than describing it as an existing owner or a settled record. Nothing below should be read as asserting that a planned document, or a decision record that has not yet been written, already governs anything. A criterion below states what finished looks like. It does not state how the work reaches it.

**Reading the citations.** Every claim about the existing system carries an inline citation of the form `[<path>:<locator>]` immediately after the claim. Citations are plain text and deliberately not hyperlinks: a plain-text citation stays meaningful in a diff and does not depend on a hosting provider's line-anchor syntax. Every line range cited here was opened and read against the working tree rather than carried over from an earlier description, and no [source member](reference/glossary-ibm-i.md#source-physical-file-and-source-member) was altered, annotated or commented to produce this document. Platform terms link to [the IBM i glossary](reference/glossary-ibm-i.md) on first use in this document.

**Figures owned elsewhere.** Each figure in this assessment has exactly one owning document, so that a number is corrected in one place. This document publishes no census of its own. Estate size, the member register and the language distribution belong to [the system inventory](current-state/01-system-inventory.md); structure, call paths and the online-to-batch duplication belong to [the current-state architecture](current-state/02-architecture-current-state.md); the platform's published support status belongs to [the platform and support status document](current-state/03-platform-and-support-status.md); columns, field types, domains and byte offsets belong to [the current data model](current-state/04-data-model-current-state.md); the rule count and the anchored-versus-unanchored split belong to [the business rule inventory](current-state/05-business-rule-inventory.md); the runtime and build sequence belong to [the operational model](current-state/06-operational-model.md); and every defect disposition belongs to [the known defects and stubs register](current-state/07-known-defects-and-stubs.md). Where a criterion below needs one of those figures, it cites the owner instead of restating the number.

**No external figure is asserted as a measurement of LIFE400.** Two of the criteria below depend on information that cannot be read out of this repository: whether a platform release still receives fixes, and how deep the labour pool for a candidate language is. Neither is quantified here. Support status is established, with attribution to the publishers that state it, in [the platform and support status document](current-state/03-platform-and-support-status.md); labour-market evidence is established, with the same discipline, in [the target-language decision matrix](talent/02-target-language-decision-matrix.md). This document states only what must become true, not how large any external population is.

**No programme schedule appears in this document.** There is no planned date, duration, sequence of calendar periods, effort estimate or staffing figure anywhere below, and none should be inferred. That is not a stylistic preference: it is the resolution recorded as A-04 in the ambiguity register, and a requirements baseline that violated its own resolution would be self-refuting. The prohibition is on *planning* in time, not on evidence that carries a date: an as-built configuration fact, a platform lifecycle date, the date of a compliance review recorded in a source banner, or the publication year of an attributed external source is evidence and is stated wherever it is load-bearing. Success is expressed as a set of verifiable end-states, and ordering — where ordering matters at all — is expressed as dependency in [the recommended path](migration/02-recommended-path.md).

## The requirement as stated

The business request is reproduced exactly as supplied, including its original grammar and its absence of terminal punctuation. Nothing is corrected, because the wording is itself evidence: it names two drivers and asks for one path, and both of those facts shape every criterion below.

> I want to plan modernization can you give me your recommended path based on our business requirements of minimizing security risk and acquiring top talent that is more familiar with modern language

That sentence is the entire requirements input. No attachment of any kind was supplied — no specification, no sample document, no diagram and no design source — and no project-specific rule was supplied either, so nothing below is derived from a template, an example or an imposed standard. In the absence of supplied rules the assessment is held to enterprise-standard documentation practice, and the practices adopted in their place are the ones this document demonstrates: an evidence citation on every claim about the existing system, one owning document per figure, immutable decision records, and structural integrity enforced by a check that runs rather than asserted in review.

Three properties of the sentence are load-bearing, and each is treated as a requirement rather than as phrasing.

- **"your recommended path" is singular and possessive.** A comparison of options does not satisfy it. The assessment commits to exactly one path and names it, and the alternatives are dispositioned explicitly so the commitment is auditable rather than asserted.
- **Two drivers are named and no others.** Minimizing security risk and acquiring talent fluent in a modern language are the only stated evaluation criteria, so every claim in this set traces to one of them. Cost, performance and feature growth are not stated drivers and are not smuggled in as if they were.
- **"plan" is the verb, not "modernize".** The deliverable is a plan. This is the single most consequential boundary in the programme, it is recorded as A-08 below, and it is the reason no ILE COBOL, ILE CL, [copybook](reference/glossary-ibm-i.md#copybook) or [DDS](reference/glossary-ibm-i.md#dds-data-description-specifications) member is changed by this work.

## Driver 1 — Minimize security risk

The first driver is stated as minimizing security risk, and it is measurable here because the risk is concrete rather than notional. It has two independent parts, and separating them is what makes the driver actionable.

The first part is beneath the application. The estate declares its runtime baseline as `ILE COBOL V3R7 · OS/400 V4R2 · IBM AS/400 Model 9406` [README.md:L264], and it declares the platform again in its header alongside the three languages it is written in [README.md:L4]. What that baseline means for fix supply is not asserted here; it is established, with attribution, in [the platform and support status document](current-state/03-platform-and-support-status.md). What matters for this driver is the shape of the exposure rather than its size: a deficiency in a layer for which no fix is issued cannot be closed by writing better application code above it.

The second part is inside the application, and every element of it is verifiable in the source. There is no identity, role, permission or encryption logic anywhere in the estate — the census establishing that, taken across all eight COBOL programs, is owned by [the current-state architecture](current-state/02-architecture-current-state.md). Access control is delegated wholly to the platform, and the application carries no notion of who is acting. The consequences are visible one by one.

- **Identity is available and then discarded.** The signed-on profile is read once [QCBLLESRC/MAINMENU.cbl:L57] and moved straight to a screen field for display [QCBLLESRC/MAINMENU.cbl:L58]. It is neither stored nor passed onward, so no decision anywhere in the estate depends on who is acting.
- **Every authenticated user reaches the identical option set.** The dispatch loop branches only on the selection typed and on two command keys, with no role, authority or permission test at any branch [QCBLLESRC/MAINMENU.cbl:L60-L92]. There is consequently no role model to migrate — one has to be derived.
- **Object authority is left at the platform default rather than hardened deliberately.** The application library is created with no authority parameter [README.md:L125], and the supporting work-management objects are created the same way [README.md:L199-L206]. One caution belongs with that observation: the only user-profile keyword anywhere in the estate is a configuration comment describing how to install the session-entry program as a user's [initial program](reference/glossary-ibm-i.md#initial-program) [QCLSRC/STRTLIFE.clle:L15], and reading it as evidence of [adopted authority](reference/glossary-ibm-i.md#adopted-authority) would misstate this system's posture.
- **Personal and health data is stored as plain character and numeric columns.** The insured's name [QDDSSRC/POLMST.pf:L32] and date of birth [QDDSSRC/POLMST.pf:L35] sit in the policy master, and a claim carries a cause of death [QDDSSRC/CLMPF.pf:L23] and a beneficiary name [QDDSSRC/CLMPF.pf:L38]. The schema declares no protection mechanism for any of them.
- **Attribution does not reach a human being.** Five programs stamp the audit item with a program-name literal rather than a user identity [QCBLLESRC/NBUWB.cbl:L138], [QCBLLESRC/NBUWMNT.cbl:L497], [QCBLLESRC/SVCBILB.cbl:L140], [QCBLLESRC/CLMADJB.cbl:L136], [QCBLLESRC/CLMMNT.cbl:L281], against an audit column whose text names it the last action user [QDDSSRC/POLMST.pf:L78]. The servicing program is not among the five: it rewrites the policy master [QCBLLESRC/SVCMNT.cbl:L190] and contains no statement that sets any audit item at all. The servicing file even declares a requesting-user column [QDDSSRC/SVCPF.pf:L51] that no writer populates, because the program writing that file declares its record as one flat two-hundred-byte area [QCBLLESRC/SVCMNT.cbl:L58] and writes it undifferentiated [QCBLLESRC/SVCMNT.cbl:L191]. Whether any of these stamps reaches the column it appears to target is a byte-offset question, answered by [the current data model](current-state/04-data-model-current-state.md) and dispositioned by [the known defects and stubs register](current-state/07-known-defects-and-stubs.md); this driver needs only the fact that no path attributes a change to a person.
- **There is no erasure path.** No program in the estate issues a record deletion, a fact whose census belongs to [the current-state architecture](current-state/02-architecture-current-state.md), so data accumulates for as long as the files exist and retention is indefinite by omission rather than by policy.
- **The only interface is a fixed character grid.** All four display files declare a twenty-four row by eighty column device — [QDDSSRC/MNUDSPF.dspf:L12], [QDDSSRC/NBUWDSPF.dspf:L14], [QDDSSRC/SVCDSPF.dspf:L14], [QDDSSRC/CLMDSPF.dspf:L13] — and a program reaches one by declaring the file as a workstation device with transaction organization [QCBLLESRC/MAINMENU.cbl:L32-L36]. What the application contributes to protecting that channel is nothing, and what a given installation configures around it cannot be read from this repository at all — the narrow, defensible statement is the one [the IBM i glossary](reference/glossary-ibm-i.md#5250-datastream) makes.
- **Nothing checks any of this on the way in.** The documented build is a sequence of platform commands with no test step and no scanning step among them [README.md:L120-L218], so no defect of this class is caught by a gate today.

None of those observations is rated here. Severity, impact and the control that closes each belong to [the security risk register](risk/01-security-risk-register.md), and the design of those controls belongs to [the target security control design](target-state/04-security-control-design.md). They appear above only because a success criterion is meaningless without the condition it is meant to replace.

SC-1.9 is included deliberately, because it is the criterion most often left out of a security case and the one that blocks the others in practice: a parallel run and a security test both need an environment that is not production, and today the target library is written into the source that reaches it.

**One clarification on SC-1.3, because the obvious phrasing of it would be unsatisfiable.** A criterion demanding a human on every mutation cannot be met by this system's own design: two of its four mutating entry paths have no contemporaneous human at all. The nightly driver runs on a schedule and takes no parameter [QCLSRC/DLYUPD.clle:L24], and a submitted job runs after its requester's session has returned [QCLSRC/RUNNBUW.clle:L43-L45], [QCLSRC/RUNNBUW.clle:L49-L50]. Writing the criterion as "a named human user" would therefore have made every scheduled or queued mutation either non-compliant by construction or compliant by fabricating a human — and the second outcome is worse than the gap it papers over, because a fabricated attribution is indistinguishable from a true one after the fact. So the criterion is met by an actor **whose type is recorded**, and the principal model that supplies human, workload and delegated identities is designed by [the target security control design](target-state/04-security-control-design.md), while the columns that hold them are typed by [the target data model and schema mapping](target-state/03-target-data-model-and-schema-mapping.md).

## Driver 2 — Acquire engineering talent fluent in a modern mainstream language

The second driver is stated as acquiring top talent more familiar with a modern language. Taken literally the phrase is unmeasurable, because "modern language" is exactly the variable the business is asking to resolve — so the interpretation is stated before any criterion depends on it. This is recorded as A-07 in the ambiguity register.

**A modern mainstream language, for the purposes of this assessment, is a general-purpose language that is currently supported by its maintainer, widely hired for, and backed by a deep enterprise labour pool.** Every clause in that reading does work. *Currently supported* excludes a language whose own runtime would inherit the problem this programme exists to remove. *Widely hired for* is the driver restated as a property of the labour market rather than of the technology, which is what makes it checkable. *Deep enterprise labour pool* narrows the reading from popularity in general to availability for regulated financial back-office work, which is what this system is. And *general-purpose* rules out a language chosen for one attractive property and then found wanting on the rest of the estate. Without that reading the driver reduces to a preference; with it, the driver produces a decision that can be defended or overturned on evidence.

What the driver is up against is not a shortage of COBOL engineers in general. It is narrower and harder than that, and the reason is visible in the estate.

- **Four platform-specific competencies are required at once, not in the alternative.** The header names three of them together — ILE COBOL, DDS and [ILE CL](reference/glossary-ibm-i.md#cl-control-language) [README.md:L4] — and the fourth is the operating system's work management, which the orchestration layer depends on rather than merely touches: a job-scoped library-list insertion [QCLSRC/STRTLIFE.clle:L27], asynchronous submission naming a [job description](reference/glossary-ibm-i.md#job-description) and a [job queue](reference/glossary-ibm-i.md#job-queue) [QCLSRC/RUNNBUW.clle:L43-L46], and job-scoped file overrides [QCLSRC/DLYUPD.clle:L60-L61]. An engineer fluent in COBOL on another platform does not arrive with those.
- **The data access model does not transfer either.** Files are reached one whole record at a time, by key, with no query language: the policy master is declared indexed with random access on a named record key [QCBLLESRC/NBUWMNT.cbl:L38-L43], and [record-level I/O](reference/glossary-ibm-i.md#record-level-io) of that kind has no counterpart in the toolchains a mainstream-language hire has used.
- **The screens are a language of their own.** Interactive programs reach a fixed twenty-four by eighty character device [QDDSSRC/MNUDSPF.dspf:L12] by declaring the file as a workstation device with transaction organization [QCBLLESRC/MAINMENU.cbl:L32-L36], which is a competency in its own right and one with no modern analogue to reason from.
- **Some of the system's behaviour exists only in the source.** The shared contract defines a rider table repeating five times [QCPYSRC/POLDATA.cpy:L88-L96], and no DDS file holds a counterpart for it, so up to five riders per policy are computed and displayed and never stored. Knowledge like that is not recoverable from the schema, from a screen or from a report; it is recoverable only by reading the copybook, which is precisely the skill the business is trying to stop depending on.
- **Most of the documented behaviour has no stable anchor to a line of source.** Only the three batch programs carry inline rule identifiers at all; `NBUWMNT`, `SVCMNT`, `CLMMNT`, `POLMSTINQ` and `MAINMENU` carry none. The census that quantifies this, and reconciles it against earlier published figures, is [the business rule inventory](current-state/05-business-rule-inventory.md).

One property of the estate constrains the answer rather than merely describing the problem, and it is the reason the language question cannot be settled on labour-market evidence alone. Money in this system is a fifteen-digit quantity with two decimal places, declared that way in the schema [QDDSSRC/POLMST.pf:L52] and again in the shared contract as thirteen integer digits and two decimals, of which exactly one field is signed [QCPYSRC/POLDATA.cpy:L106]. It is [zoned decimal](reference/glossary-ibm-i.md#zoned-decimal) — decimal in storage and decimal in arithmetic. A target language for the core must therefore offer exact decimal arithmetic at that precision as a first-class facility, never binary floating point, or premium and settlement figures will differ from the legacy system in the last place and every parity comparison will fail for a reason that has nothing to do with business logic. That is a hard filter applied before any preference is weighed, and it is why the decision is taken in [the target-language decision matrix](talent/02-target-language-decision-matrix.md) against weighted criteria rather than by acclamation. The skills position the criteria are weighed against is established in [the skills inventory and gap analysis](talent/01-skills-inventory-and-gap.md).

The two drivers converge, and the convergence is worth stating because it is the strongest form the case takes. They rest on entirely independent premises — one about the supply of platform fixes, the other about the supply of engineers — and they point at the same response. Neither is used to prop up the other, and neither is sufficient alone: hardening the application does not restore a fix supply, and hiring well does not make a platform language mainstream. Where they could pull apart is over hosting, and that tension is resolved rather than left implicit: the hardware question is separated from the language question and deferred, as recorded in A-02 below.

## Non-goals

Stated plainly, so that scope is bounded by a written list rather than by inference. Each entry is a thing this programme is not, and each traces to a resolution in the register that follows.

- **This is not a hardware-exit programme.** Moving off the AS/400 hardware is a distinct decision resting on different evidence, and it is deferred rather than rejected. To be recorded in [MOD-ADR-007](decisions/MOD-ADR-007-hardware-exit-deferred.md), a planned record, and resolved here as A-02.
- **Nothing in the running system is changed by this work.** No feature is added, no defect is fixed, no code is refactored, no performance work is done, and not one of the security findings is remediated in place. The findings are registered with a closing control; the control is designed; neither is applied here.
- **No source member is touched, in any way, for any reason.** No documentation comment, no docstring, no banner edit and no whitespace change is made to `QCBLLESRC/**`, `QCLSRC/**`, `QCPYSRC/**` or `QDDSSRC/**`. Some of the defects the register names are especially easy to misread as invitations to edit — a superseded company name on a live screen and a stale filename inside a source comment among them — and none of them is corrected. Each is recorded as a target-side action in [the known defects and stubs register](current-state/07-known-defects-and-stubs.md), which identifies that group and states the same prohibition. Resolved as A-08.
- **No implementation artifact of any kind is produced.** No target-language source, no scaffolding or prototype, no schema definition language, no data-migration or transformation script, no test code — including the characterization suite, whose strategy is to be specified in [the characterization test strategy](migration/05-characterization-test-strategy.md), a planned document, without the suite itself being written — no pipeline configuration, and no container or infrastructure definition.

## How success is verified

Four mechanisms operate over this documentation set. They check structure and traceability, which is all a documentation deliverable can be checked for; none of them checks behaviour, and the reason is stated below rather than left as an impression.

- **Site build.** `mkdocs build --strict`, which turns a document missing from navigation or a broken internal link into a build failure rather than a warning. It reads a root `mkdocs.yml` carrying the navigation, which is planned rather than present, so this mechanism is the one of the four that does not yet operate. Python dependencies are pinned exactly, `mkdocs==1.6.1` and `mkdocs-material==9.7.7`, in `requirements-docs.txt`.
- **Markdown lint.** `markdownlint-cli2@0.23.2` against the committed `.markdownlint-cli2.jsonc`, which enforces a single first-line heading and a language identifier on every fenced block, and which excludes the machine-generated corpus.
- **Link resolution.** `markdown-link-check@3.15.0` against the committed `.mlc-config.json`, driven per file. While the set is still being written, a link into a planned-but-unwritten document is reported as unresolved; that is the check working rather than a defect in the document that links forward.
- **Citation resolution.** A pattern extracts every `[<path>:<locator>]` reference from the set and asserts that the path exists in the working tree and that the line range lies within that file's length. This is the only automated accuracy gate available, and its limit is worth stating: it proves that a citation resolves, never that the range holds the construct claimed. Every citation in this document was additionally checked by opening the member.

Diagram parsing is checked with `@mermaid-js/mermaid-cli@11.16.0` for the documents that carry diagrams. This document carries none by design — every diagram in the set is assigned to another document — and its obligation to present structured rather than purely narrative content is met by the tables above. No tool version is ever expressed as a floating range: the theme warns that the next major release of the site generator changes its plugin and theming systems with no migration path, so every version is pinned exactly.

**A pin states which tool runs; it does not state what the tool needs in order to run, and a gate nobody can start is not a gate.** So the interpreter and runtime floors for all five pinned packages are documented once, in the repository overview's Documentation section [README.md:L88-L116], and are deliberately not restated here: Python 3.8 or newer for the site generator and its theme, and Node 22 or newer together with `npx` for the three validators, each floor being the one the package's own metadata declares rather than a local preference. Two properties of that arrangement matter to this document. The prerequisites belong to the **documentation toolchain and to nothing else** — no runtime dependency of LIFE400 changes anywhere in this assessment, and its declared platform baseline [README.md:L264] is untouched. And `npx` is used precisely so that no Node manifest is added to a repository whose members are ILE COBOL, ILE CL and DDS, which is the same reasoning that keeps the four configuration files at the root from growing a fifth.

**No command can compile, bind or execute LIFE400, and no criterion above should be read as build-verified.** ILE COBOL and ILE CL require the IBM i platform, every COBOL program names that platform as its object computer as well as its source computer, and no off-platform compiler for either language exists; the evidence for that lock is assembled in [the platform and support status document](current-state/03-platform-and-support-status.md). There is likewise no test suite to run: the repository's own structure diagram enumerates every directory and member the estate holds and not one of them is a test member or a test-runner configuration [README.md:L27-L55], and the documented build is eight steps of platform commands with no test step among them [README.md:L120-L218]. Behavioural accuracy in this set therefore rests on citation resolution and human review, and on nothing else. That absence is also why the migration is gated on a behavioural baseline before any conversion, to be recorded in [MOD-ADR-008](decisions/MOD-ADR-008-characterization-tests-first.md), a planned record — the criteria in this document describe the end-state, and that record will describe the safety net without which reaching it cannot be demonstrated.
